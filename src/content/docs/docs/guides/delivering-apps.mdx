hyve delivers everything with [Fleet](https://fleet.rancher.io/). A **Deployment** is one Fleet
`HelmOp`, `Bundle` or `GitRepo`, and `--to` says which clusters get it. See
[Deployments](/docs/concepts/deployments) for the model.

| You want it on | `--to` | Lives in |
|---|---|---|
| every cluster made from a template | `template/NAME` | the template namespace |
| every cluster of a ClusterClass | `class/NAME` | the template namespace |
| every cluster in an environment | `env/NAME` | the environment |
| one cluster | `cluster/ENV/NAME` | the cluster's environment |
| clusters with some labels | `group/NAME`, a ClusterGroup of your own | the template namespace |
| every cluster hyve manages | `all` | the template namespace |
| the management cluster itself | `host` | `fleet-local` |

`--to` is repeatable: `--to template/civo-small --to template/capd-small` is one Deployment on
both. hyve picks where it lives from its targets; `-n` sets it.

The source is one of:

| Source | Flags |
|---|---|
| a Helm chart | `--helm CHART --repo URL --version V`, or `--helm oci://...` |
| manifests on your machine | `--path FILE-or-DIR` (sent inline, as a Fleet Bundle) |
| a git repository | `--git URL` with `--branch` or `--revision`, and `--git-path` (repeatable) |

and the options: `-N` (the namespace its objects go in on the cluster), `--set key=value` and
`-f values.yaml` (Helm values), `--release-name`, `--secret NAME` (repeatable),
`--correct-drift` (Fleet undoes changes made on the cluster), `--rollout` and `--paused`.
`--dry-run` prints the Fleet object instead of saving it.

## On every cluster from a template

```bash
hyve deploy create traefik --helm traefik \
    --repo https://traefik.github.io/charts --version 37.1.0 \
    -N traefik --set service.type=LoadBalancer --to template/capd-small
```

Clusters already made from the template get it as well as new ones. As YAML, for
`hyve apply -f` (or `hyve deploy apply -f`) or `kubectl apply`, it's a plain Fleet HelmOp:

```yaml
apiVersion: fleet.cattle.io/v1alpha1
kind: HelmOp
metadata:
  name: traefik
  namespace: capi-clusters
spec:
  defaultNamespace: traefik
  helm:
    repo: https://traefik.github.io/charts
    chart: traefik
    version: 37.1.0
    releaseName: traefik
    values:
      service: {type: LoadBalancer}
  targets:
    - clusterGroup: template-capd-small
```

Pin chart versions. Without one, each cluster gets whatever is newest when Fleet installs it.

Values can use Fleet's templating, such as `${ .ClusterName }`, for what differs per cluster.

## On one cluster, or one environment

```bash
hyve deploy create podinfo --helm podinfo \
    --repo https://stefanprodan.github.io/podinfo --version 6.7.1 --to cluster/prod/web
hyve deploy create base --path ./manifests --to cluster/prod/web
hyve deploy create debug-tools --path ./debug --to env/dev
```

A Deployment whose targets are all in one environment lives in that environment's namespace, so
the environment's members can make and change it ([Users and access](/docs/concepts/access)).
It can then only target that environment's clusters.

Deleting a cluster leaves the Deployments aimed at it; delete one aimed only at that cluster with
`hyve deploy delete`.

## On several templates, or every cluster of a class

One Deployment can have several targets, so there's nothing to share by reference:

```bash
hyve deploy create external-dns --helm external-dns \
    --repo https://kubernetes-sigs.github.io/external-dns/ --version 1.19.0 \
    -N external-dns -f external-dns-values.yaml --secret cloudflare-dns \
    --to template/civo-small --to template/civo-large
hyve deploy update external-dns --add-to class/civo     # every Civo cluster instead
hyve deploy update external-dns --remove-to template/civo-small --remove-to template/civo-large
```

For a set of clusters no template, class or environment describes, make a ClusterGroup of your
own in the template namespace (in the UI: **Fleet**, show **Groups**, **New group**) and target
`group/NAME`:

```yaml
apiVersion: fleet.cattle.io/v1alpha1
kind: ClusterGroup
metadata:
  name: edge
  namespace: capi-clusters
spec:
  selector:
    matchLabels:
      site: edge
```

## Rolling out a change

```bash
hyve deploy update podinfo --version 6.8.0 --rollout one-at-a-time --wait
```

`update` changes only what's given. `--version`, `--set` and `-f` change a chart's version and
values (`--set` and `-f` merge over the values it has); `--revision`, `--branch` and `--git-path`
change a git source's. `--helm`, `--git` or `--path` replace the whole source instead, so give
the rest of it with them. Targets and the rollout change only when given.

`--wait` returns once every cluster it targets runs the change and is ready, and fails if one
can't: a chart version that doesn't exist, a cluster that can't apply it, or `--timeout` (10
minutes) passing first. `hyve deploy wait podinfo` does the same on its own.

| `--rollout` | |
|---|---|
| `all` | Every cluster at once (the default). |
| `one-at-a-time` | One cluster at a time; a cluster that doesn't come back ready stops the rest. |
| `canary` | The same, clusters labelled `hyve.io/canary=true` first. |

Rollout is for Helm charts and manifests. A git source's is per bundle, in its `fleet.yaml`.

<Steps>

1. Pause it, so changes wait:

   ```bash
   hyve deploy pause podinfo
   ```

2. Change it. Nothing reaches clusters yet; what's deployed stays.

3. Let it go:

   ```bash
   hyve deploy resume podinfo
   ```

</Steps>

`hyve deploy force podinfo` deploys again to every cluster, even where nothing changed.

## Secrets they need

A Deployment names the Secrets it needs with `--secret`. The Secrets stay on the management
cluster, in the Deployment's namespace, and Fleet copies them to each cluster it reaches, into
the namespace it deploys to. hyve holds no values: create the Secrets with
`hyve deploy secret create`, or however your install manages secrets (External Secrets, the Infisical
operator, sealed-secrets).

```bash
CF_TOKEN=... hyve deploy secret create cloudflare-dns --from-env api-token=CF_TOKEN
hyve deploy secret list        # what each Deployment needs, and whether it exists
```

A git source can't copy Secrets this way; list them under `downstreamResources` in the repo's
`fleet.yaml`. See [Secrets](/docs/concepts/secrets).

## A git repository, kept in sync

For a repository laid out for Fleet (a `fleet.yaml` per directory, one bundle each):

```bash
GIT_TOKEN=... hyve deploy create apps --git https://github.com/example/platform.git \
    --git-path apps --username me --token-env GIT_TOKEN --to env/prod
```

hyve keeps the username and token in a basic-auth Secret, `apps-git-auth`, that the GitRepo
uses. Any git host works.

`--to host` puts the GitRepo in `fleet-local`, the management cluster itself: use it for what
the management cluster runs, such as ClusterClasses, templates and Deployments kept in git.
(This replaces `hyve repo add`.)

## Checking what's where

```bash
hyve deploy list                     # every Deployment: source, targets, rollout, clusters ready
hyve deploy show podinfo             # its state on each cluster; -o yaml for the Fleet object
hyve cluster deployments web -e prod # what's on a cluster, why, and its state there
```

In the UI, **Fleet** lists Deployments, groups and a deployment-by-cluster status matrix, and a
cluster's **Deployments** tab shows what reaches it and why.

## Coming from template resources

Templates used to carry a `resources` list, clusters had `ClusterResource` extras, and shared
`Resource`s were referred to with `--ref`. hyve-controller turns all of them into Deployments on
upgrade, without redeploying anything. See
[Migrating from template resources](/docs/concepts/deployments#migrating-from-template-resources).
