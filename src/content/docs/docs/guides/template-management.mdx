## Overview

Templates capture a cluster's shape — which module drives it, its region, and its params — once, so you can stamp out consistent clusters by name instead of retyping the same flags every time.

## Template Basics

### What are Templates?

A template combines:
- A **driver** — the module (`spec.driver.source`/`version`) that implements create/delete/status/auth for a specific provider
- A **region** and **params** — the module-specific settings (`node_size`, `instance_type`, whatever the module's `module.yaml` declares)
- **Lifecycle workflows** — `beforeCreate`/`onCreate`/`afterCreate`/`onDelete`/`afterDelete`, run automatically at each stage
- Optionally, a **schedule** — a cron expression that auto-expires every cluster created from this template

### Creating Templates

```bash
hyve template create prod-template \
  --driver github.com/hyve-modules/civo \
  --driver-version v1.0.0 \
  --region NYC1 \
  --set node_size=g4s.kube.large \
  --set node_count=3
```

<Note>
  There's no interactive "quick create" shortcut beyond flags — every param the module needs goes through `--set KEY=VALUE`, repeatable.
</Note>

Or write the YAML directly:

```yaml
# templates/prod-template.yaml
apiVersion: hyve.io/v1alpha1
kind: Template
metadata:
  name: prod-template
  description: Production cluster with monitoring
spec:
  driver:
    source: github.com/hyve-modules/civo
    version: v1.0.0
  region: NYC1
  params:
    node_size: g4s.kube.large
    node_count: "3"
  workflows:
    onCreate:
      - setup-monitoring
      - deploy-app
    onDelete:
      - backup-data
```

## Template Structure

### Complete Template Example

```yaml
apiVersion: hyve.io/v1alpha1
kind: Template
metadata:
  name: production-standard
  description: Standard production cluster with 3 large nodes and observability
spec:
  driver:
    source: github.com/hyve-modules/civo
    version: v1.0.0
  region: NYC1
  params:
    node_size: g4s.kube.large
    node_count: "3"
  workflows:
    onCreate:
      - setup-monitoring
      - configure-logging
      - deploy-observability
      - setup-backups
    onDelete:
      - export-logs
      - final-backup
```

### Template Fields

```yaml
metadata:
  name: my-template                 # Required
  description: What it creates      # Optional

spec:
  driver:                           # Required — which module drives this cluster
    source: github.com/hyve-modules/civo
    version: v1.0.0

  runner:                           # Optional — cluster-mode Job image override
    image: ""                       #   falls back to HyveConfig.spec.defaultModuleImage if unset

  region: NYC1                      # Passed to the module as part of cluster context

  params:                           # Arbitrary key/value pairs, module-specific — injected
    node_size: g4s.kube.large       #   as HYVE_PARAM_<KEY> env vars for every module operation
    node_count: "3"

  workflows:                        # Optional — lifecycle hooks
    beforeCreate:                   #   Before provisioning (no kubeconfig yet)
      - provision-prereqs
    onCreate:                       #   After the cluster is ready, before spec.resources applies
      - setup-monitoring
      - deploy-app
    afterCreate:                    #   After spec.resources has applied
      - notify-team
    onDelete:                       #   Before deletion
      - backup-data
    afterDelete:                    #   After deletion (no kubeconfig)
      - teardown-prereqs
    preReconcile:                   #   Every reconcile cycle, before drift is resolved
      - refresh-secrets

  resources: []                     # Optional — Kubernetes manifests hyve owns and re-applies;
                                     #   see /docs/concepts/resources

  schedule: "0 20 * * 5"            # Optional — cron expression. A cluster created from this
                                     #   template gets spec.expiresAt set to the next occurrence
                                     #   (e.g. every Friday at 20:00), computed at creation time.

  lockParams: []                    # Optional — param names whose values are hashed and locked
                                     #   at creation time, so `hyve cluster adopt`'s drift
                                     #   detection knows they were intentional, not drift
```

<Info>
  `params` is a flat string map — its keys are entirely up to the module. Check the module's own `module.yaml`/README for which params it expects (e.g. `node_size`/`node_count` for a Civo module, `instance_type`/`node_count` for an EKS module) — there's no fixed, hyve-defined schema of provider-specific fields.
</Info>

## Executing Templates

### Basic Execution

```bash
hyve cluster create prod-cluster-01 --template prod-template
```

**This command:**
1. Loads the template, applies any `--region`/`--set` overrides
2. Computes `spec.expiresAt` if the template has a `schedule`
3. Generates the cluster YAML
4. Runs reconciliation: `beforeCreate` → provision → wait for `ACTIVE` → merge kubeconfig → `onCreate` → apply `spec.resources` → `afterCreate`

```bash
# Override region and a param for this specific cluster
hyve cluster create eu-cluster-01 --template prod-template \
  --region FRA1 \
  --set node_count=5
```

## Template Management

### Listing Templates

```bash
hyve template list
```

### Showing Template Details

```bash
hyve template show production-standard
```

Prints the full template YAML.

### Deleting Templates

```bash
hyve template delete old-template
```

<Note>
  Deleting a template doesn't touch clusters already created from it — a cluster's YAML is a full, independent copy of what the template generated, not a live reference back to it.
</Note>

## Validating Templates

```bash
hyve template validate production-standard
```

Checks the template's structure — required fields, that referenced workflows exist, that `schedule` (if set) is a valid cron expression. It does not validate the module's own params against a schema (there isn't one to check against) or reach out to the cloud provider.

## Template Examples

### Development — small, no schedule

```yaml
apiVersion: hyve.io/v1alpha1
kind: Template
metadata:
  name: dev-template
  description: Small development cluster
spec:
  driver:
    source: github.com/hyve-modules/civo
    version: v1.0.0
  region: PHX1
  params:
    node_size: g4s.kube.small
    node_count: "1"
```

### Ephemeral — auto-expires

```yaml
apiVersion: hyve.io/v1alpha1
kind: Template
metadata:
  name: feature-env
  description: Short-lived feature-branch cluster, auto-deleted weekly
spec:
  driver:
    source: github.com/hyve-modules/civo
    version: v1.0.0
  region: PHX1
  params:
    node_size: g4s.kube.small
  schedule: "0 20 * * 5"   # every Friday at 20:00
  workflows:
    onCreate:
      - deploy-app
      - seed-data
    onDelete:
      - notify-team
```

### AWS EKS — a different module, same shape

```yaml
apiVersion: hyve.io/v1alpha1
kind: Template
metadata:
  name: aws-eks-template
  description: Production EKS cluster
spec:
  driver:
    source: github.com/hyve-modules/eks
    version: v2.1.3
  region: us-east-1
  params:
    instance_type: t3.medium
    node_count: "3"
    vpc_id: vpc-0abc123456789
    eks_role_arn: arn:aws:iam::123456789012:role/eks-role
    node_role_arn: arn:aws:iam::123456789012:role/node-role
  workflows:
    onCreate:
      - deploy-app
```

<Note>
  Every provider is the same template shape — only `driver.source`, `region`, and which `params` keys the module expects change. If a param (like a VPC ID) needs to come from a `beforeCreate` workflow instead of being hardcoded, have that workflow emit it as a `HYVE_KEY=value` output line and reference `${HYVE_KEY}` in a downstream step or resource — see [Workflow Variables](/docs/workflows/variables).
</Note>

## Use Cases

### Rapid Environment Provisioning

<Steps>
  <Step title="Create the template once">
    ```bash
    hyve template create feature-env \
      --driver github.com/hyve-modules/civo --driver-version v1.0.0 \
      --region PHX1 --set node_size=g4s.kube.small
    ```
  </Step>

  <Step title="Spin up environments on demand">
    ```bash
    hyve cluster create feature-auth --template feature-env
    hyve cluster create feature-payments --template feature-env
    ```
  </Step>

  <Step title="Clean up when done">
    ```bash
    hyve cluster delete feature-auth
    hyve cluster delete feature-payments
    ```
  </Step>
</Steps>

### Standardized Production Clusters

```bash
hyve cluster create prod-api-01 --template production-template
hyve cluster create prod-api-02 --template production-template
hyve cluster create prod-web-01 --template production-template
# Same driver, same params, same workflows — every time
```

### Testing Different Drivers

```bash
hyve template create test-k3s --driver github.com/hyve-modules/civo --driver-version v1.0.0 --region PHX1 --set node_size=g4s.kube.medium
hyve template create test-talos --driver github.com/hyve-modules/civo-talos --driver-version v1.0.0 --region PHX1 --set node_size=g4s.kube.medium

hyve cluster create test-k3s-cluster --template test-k3s
hyve cluster create test-talos-cluster --template test-talos
```

## Best Practices

<AccordionGroup>
  <Accordion title="Name templates by purpose">
    ```bash
    # Clear
    hyve template create production-ha --driver ... --region ...
    hyve template create staging-standard --driver ... --region ...

    # Unclear — avoid
    hyve template create template1 --driver ... --region ...
    ```
  </Accordion>

  <Accordion title="Write a description">
    ```yaml
    metadata:
      name: production-standard
      description: Standard production cluster with HA, monitoring, and backups
    ```
  </Accordion>

  <Accordion title="Include essential workflows">
    ```yaml
    spec:
      workflows:
        onCreate:
          - setup-monitoring
          - configure-logging
          - setup-backups
          - deploy-app
        onDelete:
          - export-logs
          - final-backup
    ```
  </Accordion>

  <Accordion title="One template per environment tier">
    ```bash
    hyve template create dev-template --driver ... --region PHX1 --set node_size=g4s.kube.small
    hyve template create staging-template --driver ... --region PHX1 --set node_size=g4s.kube.medium
    hyve template create prod-template --driver ... --region NYC1 --set node_size=g4s.kube.large
    ```
  </Accordion>

  <Accordion title="Version control templates">
    If your environment directory is git-backed (optional — see [Version Control](/docs/concepts/gitops)), commit template changes with descriptive messages, same as any other file:

    ```bash
    git commit -am "Add production-ha template with 5-node configuration"
    git log templates/production-standard.yaml
    ```
  </Accordion>

  <Accordion title="Validate before creating a cluster from it">
    ```bash
    hyve template validate my-template
    hyve cluster create new-cluster --template my-template
    ```
  </Accordion>
</AccordionGroup>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Cluster creation from a template fails">
    ```bash
    # 1. Validate the template first
    hyve template validate my-template

    # 2. Check the module's own credential requirements are met
    #    (e.g. for Civo: civo apikey list)

    # 3. Review the template
    hyve template show my-template
    ```
  </Accordion>

  <Accordion title="Workflows fail after the cluster is created">
    The cluster still exists — re-run workflows manually once you've fixed the underlying issue:

    ```bash
    hyve cluster auth my-cluster
    hyve workflow run setup-monitoring --cluster my-cluster
    hyve workflow validate setup-monitoring
    ```
  </Accordion>

  <Accordion title="Template not found">
    ```bash
    hyve template list
    ls "$(hyve env path)/templates/"

    # If git-backed, pull the latest first
    git pull

    # Create it if it's genuinely missing
    hyve template create my-template \
      --driver github.com/hyve-modules/civo --driver-version v1.0.0 \
      --region PHX1 --set node_size=g4s.kube.medium
    ```
  </Accordion>

  <Accordion title="Cluster name already exists">
    ```bash
    hyve cluster create prod-cluster-02 --template prod-template
    # or
    hyve cluster delete prod-cluster-01
    hyve cluster create prod-cluster-01 --template prod-template
    ```
  </Accordion>
</AccordionGroup>
