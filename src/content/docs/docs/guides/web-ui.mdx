---
title: The web UI
description: Open hyve's UI, what each page does, the Explorer for any cluster's objects, and the kubectl shell.
---

The hyve host serves a web UI for everything the CLI does: clusters, templates, Deployments,
secrets, providers, users and access, plus an Explorer for any object on any cluster
and a kubectl shell in the browser. It's built into hyve's binary, so nothing more is
installed. Everything in it runs as the signed-in user, through the same proxy as kubectl, so
your RBAC decides what you see and change.

## Opening it

```bash
hyve ui
```

`hyve ui` opens the UI for the current context in your browser, already signed in: the browser
gets a session of its own made from the CLI's, so there's no password to type. `--server NAME`
opens another saved server; `--no-browser` prints the URL instead.

When the host's certificate comes from a CA the browser doesn't trust (local mode's, or a
private one you gave `hyve login --ca-cert`), `hyve ui` serves the UI itself at
`http://127.0.0.1:30445`, trusting the CA on the browser's behalf, until you press Ctrl-C.
`--port` picks another port (`0` for any free one); if 30445 is taken, it uses a free one.

Otherwise, go to the host's URL and sign in with your username and password, or through the
identity provider when the host has one ([Signing in with OIDC](/docs/guides/oidc)). A user who
must change their password does it on the sign-in page.

In local mode, `hyve local ui` is the same as `hyve ui --server local`.

## Pages

The sidebar shows what your access lets you use.

| Page | What it does | CLI |
|---|---|---|
| **Overview** | every cluster with its provider, template, environment, phase and expiry; each running cluster's CPU, memory and pods (used, or requested where the cluster has no metrics-server); Deployments failing anywhere, the host's included; clusters expiring soon | `hyve cluster list` |
| **Clusters** | the clusters in an environment. Create one from a template, adopt an existing one through a template's provider, or import one from its kubeconfig ([Bringing in existing clusters](/docs/guides/existing-clusters)); open one to scale its control plane and worker pools, change its expiry, upgrade its Kubernetes version, download a kubeconfig, edit its YAML, or delete it (detach it, when imported) | `hyve cluster` |
| **Templates** | view, create and edit ClusterTemplates, preview what a cluster made from one gets, or make a cluster from it. **Apply YAML** also takes a ClusterClass and its provider templates, and Fleet GitRepos, HelmOps, Bundles and ClusterGroups. A template's page has **Deployed to its clusters**: the Deployments that reach every cluster made from it (aimed at it, its class or all clusters), with **Deploy to this template** | `hyve template`, `hyve template render` |
| **Fleet** | every Deployment with its source, targets, rollout, clusters ready and state. **Show** picks a category: all of them; **Templates**, **Environments**, **Cluster classes** or **Groups**, a section for each with its clusters and what's aimed at it; **Clusters**, a section for each with each Deployment's state there; or **No target**, those reaching no cluster. A second dropdown narrows a category to one template, environment, class, group or cluster; search and state narrow further. Pages of 25, 50 or 100 rows. Under **Groups**, **New group** makes a custom group by labels, and each group's **Delete group** removes it. **New deployment**. A Deployment's page ends with deleting it | `hyve deploy`, `hyve deploy secret` |
| **Providers** | the installed Cluster API providers and their health; add and remove them. Adding one can also install the ClusterClasses it publishes | `hyve provider` |
| **People** | two tabs. **Users**: hyve's users (create, invite, set passwords, disable, groups; service users for CI), each with what they and their groups may reach; a user's **Tokens** (API tokens) and **CI sign-in** (the CI systems' jobs that may sign in as them). **Access**: who can reach which clusters; grant and revoke owner, member and read-only roles, environment membership, and deploying to templates, for everyone or one user | `hyve user`, `hyve access` |
| **Environments** | create and delete environments | `hyve env` |
| **Explorer** | the management cluster's objects (below). Shown to users who may list its namespaces | `kubectl` |

Old hyve Templates and herd ClusterTemplates can be pasted or loaded from files at `/import`
and converted, as `hyve template convert` does ([Importing old templates](/docs/guides/importing)). Any
kind the cluster serves can be listed at `/list/<type>` and edited as YAML; that's the way to
manage what has no form of its own.

Each cluster's page has three tabs: **Overview** (a resource monitor, then its fields,
conditions, variables, size and expiry), **Deployments** (each Deployment that reaches it, why, and its state there; **Deploy to
this cluster** and **Deploy to every *template* cluster**; and the Secrets its Cluster API
provider and its environment's Deployments need) and **Explorer**.

The resource monitor, on each cluster's page and the host's (**local**), reads the cluster every
15 seconds while the page is in view: CPU, memory and pods as gauges of what's used, requested
and limited against what the nodes can give (allocatable); each node's state, pressure and
load; and the latest warning events. Usage comes from metrics-server. A cluster without it
shows requests only; deploying the `metrics-server` chart to it (a Deployment, like any app)
adds usage. Local mode's host doesn't run metrics-server.

The account menu has **API tokens**: your own, for scripts and CI.

The old Shared resources and Repos pages are gone; their URLs open **Fleet**.

## Deployments

A Deployment's page shows where it's delivered, how many clusters are ready, any problem, its
rollout, its state on each cluster, and its bundles, opened to what they deployed. Its Secrets
are listed with whether each exists. **Pause**/**Resume**, **Deploy again**, **YAML**,
**Delete** and **Edit** are at the top.

The form (**New deployment**, or **Edit**) has:

- a name, and a source: **Helm chart**, **Git repository** or **Manifests**. A private git
  repository takes a username and token, kept in a basic-auth Secret, `NAME-git-auth`;
- **Deliver to**: any of Template, Cluster class, Environment, Cluster, Group, All clusters and
  Host cluster;
- **Roll out changes**: All at once, One cluster at a time, or Canary clusters first (not for
  git, whose `fleet.yaml` says);
- **Secrets to copy**, and **Paused**.

**Edit as YAML** opens the Fleet object itself, for whatever the form doesn't cover. See
[Deployments](/docs/concepts/deployments).

## Secrets

Secrets are listed where they're used: a Deployment's on its page, a cluster's on its
Deployments tab. Those lists include Secrets that git sources name in their `fleet.yaml`. One an operator
syncs (Infisical's, External Secrets) shows what manages it and isn't edited there, since the
next sync would undo the edit. Any other Secret is in the Explorer.

## The Explorer

The Explorer lists every resource type a cluster serves, the way `kubectl get` lists them, and
opens each object. Each cluster has one on its Explorer tab; the management cluster's is the
Explorer page.

- **Types** are in a sidebar grouped by API group, with the common ones (Pods, Deployments,
  Services, ...) first and the ones you opened recently above them. Find a type by name. On a
  phone the list is a drawer.
- **Lists** show the same columns as `kubectl get`, with status pills, ages instead of
  timestamps, and the namespace under each name. The columns menu adds the ones
  `kubectl get -o wide` adds. Filter by namespace, search by name, or give a label selector
  (`app=web`) and press Enter. Lists stay live: the host watches them as you and the page
  updates.
- **Create** adds an object of the listed type, in the list's namespace: a Secret in the
  key/value form, anything else as YAML from a starting point. It fails if the name is taken,
  so it never changes another object.
- **An object** opens with its kind, namespace, labels and owners, and tabs:
  - **YAML**, to view, or edit and save with server-side apply. A conflict with another
    change is reported, and you can overwrite it.
  - For a Secret, its **keys** above the YAML, decoded: show or copy each value. **Edit** opens
    the key/value form (values typed as text, or from a file); **Edit YAML** edits the raw object.
    **Show values (decoded)** shows the YAML's text values as `stringData`.
  - **Events** for the object, warnings marked.
  - For a pod, **Logs** (followed as they're written, per container, downloadable) and
    **Shell** (a shell in a container, through the proxy as you).
  - **Delete**, when you're allowed to.

The URL holds where you are (type, namespace, object and tab), so it can be bookmarked and
shared. Cmd- or Ctrl-click a row to open it in a new tab.

## The kubectl shell

The **kubectl shell** button on a cluster's page (and on the management cluster's Explorer)
docks a terminal with `kubectl`, `helm`, `k9s` and `kustomize`, already pointed at that
cluster.

It runs as you. The host starts a short-lived pod in the `hyve-shell` namespace on the cluster,
from `rancher/shell`, with a ServiceAccount that may only impersonate you and your groups. So
the cluster's RBAC decides every command, as through the proxy, and no hyve session is stored
on the cluster. It works on [push](/docs/concepts/delivery) clusters too, since nothing in the
pod has to reach the host.

- A shell lasts at most an hour. Closing the terminal deletes its pod; one the host couldn't
  clean up ends at that deadline, and the next shell on the cluster removes it.
- The first shell on a new node waits for the image to be pulled.
- The chart's `host.shell.image` sets the image; empty turns the shell off.

## Turning the UI off

The chart's `ui.enabled` (on by default) decides whether the host serves the UI. Off, the host
still serves sign-in, the agent tunnel and the proxy, so the CLI and kubectl work as before.
Pass it to `hyve install -f values.yaml`:

```yaml
ui:
  enabled: false
```
