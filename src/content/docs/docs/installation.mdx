hyve is one binary: the CLI, hyve-controller and the host endpoint. The web UI is embedded in
it when it's built.

<Aside type="caution" title="Build v2 from source">
The hyve described on this site is the `v2` branch of
[cbridges1/hyve](https://github.com/cbridges1/hyve), which has no release yet. Until it does,
`go install github.com/cbridges1/hyve@latest` installs the old hyve (v1), and
`go install github.com/cbridges1/hyve@v2` doesn't resolve. Build it from a checkout as below.
</Aside>

## Prerequisites

| Tool | For |
|---|---|
| Go 1.26 or later | building the binary |
| Node.js and npm | building the web UI the binary embeds (optional: without it, the binary has no UI) |
| [Task](https://taskfile.dev) | the build tasks below (optional: each is one command you can run by hand) |
| Docker | local mode, and building hyve's image |
| kubectl | optional; hyve doesn't need it, but you'll want it for the clusters you make |

## Build the CLI

```bash
git clone -b v2 https://github.com/cbridges1/hyve.git
cd hyve
task ui      # builds the UI into internal/webui/dist (npm ci, npm run build in ui/)
task build   # go build -o hyve .
```

Then put `./hyve` on your `PATH`, for example:

```bash
sudo install hyve /usr/local/bin/
hyve --version   # a build from source says "hyve dev"
```

`task build` without `task ui` first gives a binary with no web UI.

## Build the image

hyve-controller and the host run from hyve's image. A release uses its published image
(`ghcr.io/cbridges1/hyve`). A build from source has none, so build one from the same checkout:

```bash
task image   # docker build -t hyve:dev .
```

The Dockerfile builds the UI itself, so `task ui` isn't needed for the image.

- **Local mode** uses `hyve:dev` by default when the binary is a build from source, and
  imports it from your Docker into the local cluster. `task local` builds the binary and the
  image, then runs `hyve local up` with it.
- **A standalone install** needs an image the cluster can pull: push `hyve:dev` to a
  registry the cluster can reach and pass it with `hyve install --image`. Without `--image`, a
  build from source refuses to install rather than deploy an image that doesn't exist.

## Where hyve keeps things

Everything the CLI saves is under `~/.hyve` (or `--home`, or `HYVE_HOME`): the servers you've
signed in to and their sessions, and local mode's kubeconfig, certificates and saved state. Your
`~/.kube/config` is only changed by `hyve cluster auth`.
