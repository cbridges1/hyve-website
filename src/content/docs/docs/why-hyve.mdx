---
title: Why hyve
description: What hyve adds to Cluster API and Fleet, and what it leaves to them
---

Cluster API makes Kubernetes clusters from a `ClusterClass`, on any infrastructure that has a
provider. Fleet puts Helm charts, manifests and git repositories on clusters and keeps them
there. Between them they do most of what a cluster platform needs. What they don't give you
is the part people use day to day:

- **A shape people can pick without knowing every variable.** A ClusterClass exposes
  variables; it doesn't say which values to use, which ones nobody should change, or when a
  cluster should go away.
- **The apps every cluster of that shape needs.** A CNI, an ingress controller, DNS,
  monitoring: Fleet can deliver them, but something has to aim them at the right clusters.
- **A place to sign in.** Users need kubectl access to the clusters they're allowed to use,
  with their own identity, not a copy of each cluster's admin kubeconfig.

hyve is that part, and only that part.

## What hyve adds

| | What it is |
|---|---|
| **ClusterTemplate** | A ClusterClass with defaults, locked variables, an expiry schedule and the resources every cluster made from it gets. A webhook fills in and guards any Cluster labelled with the template, however it was created: the CLI, `kubectl`, GitOps or the UI. |
| **Resources** | Each template resource is Fleet's own `HelmOp`, `Bundle` or `GitRepo` spec. hyve-controller turns it into a Fleet object aimed at the template's clusters. A cluster can have extras of its own. |
| **Expiry** | hyve-controller deletes a cluster when its `hyve.io/expires-at` passes, set from the template's cron schedule or from `--ttl`. |
| **The host endpoint** | The server users sign in to (with a password, or through an OpenID Connect provider) and that every child cluster's agent connects to. kubectl, Helm and k9s reach each cluster through it as the signed-in user. It also serves the web UI. |
| **Environments** | Namespaces on the management cluster that hold clusters, with roles for who can create clusters there and who can use each one. |

## What hyve leaves to others

- **Making clusters** is Cluster API's job, through whichever providers you install (Docker,
  AWS, Azure, GCP, Civo, or your own). hyve has no provisioning code.
- **Delivering apps** is Fleet's job. hyve writes Fleet objects; Fleet and its agent do the
  rest. A cluster whose agent can't connect gets the same Fleet deployments pushed from the
  management side ([delivery](/docs/concepts/delivery)).
- **Secrets** are plain Kubernetes Secrets. A resource names the Secrets it needs and Fleet
  copies them to its clusters. hyve holds no secret values, so fill them however you already
  do (an operator, sealed secrets, `kubectl`).
- **The agent on each cluster** is Rancher's own `cattle-cluster-agent`, pinned to a tested
  version. hyve serves the small part of Rancher's server the agent needs.

## Compared with Rancher

hyve covers what Rancher's cluster management does for Cluster API clusters: one place to
sign in, a proxy to every cluster, role bindings per cluster and per environment, and Fleet
for delivery. It doesn't have Rancher's other products (its own provisioning, projects,
monitoring and logging apps, the app catalog). It's much smaller: hyve-controller and the
host together use tens of megabytes.

If you run Rancher today with Turtles for Cluster API, `hyve install --replace-rancher`
moves a cluster over while Fleet and Cluster API keep running
([Replacing Rancher](/docs/running/replacing-rancher)).

## One model, two ways to run

The objects and commands are the same whether hyve runs on a server or on your laptop:

- **[Standalone](/docs/running/standalone):** `hyve install` on any cluster you choose, for a
  long-lived platform with users, the UI and single sign-in.
- **[Local mode](/docs/running/local-mode):** `hyve local up` on a K3s container the CLI
  manages, for laptops and CI pipelines, with nothing to run yourself.
