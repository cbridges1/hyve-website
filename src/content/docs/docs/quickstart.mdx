This runs hyve in [local mode](/docs/running/local-mode) and makes a cluster with CAPD,
Cluster API's Docker provider, so everything runs as containers on your machine. You need
Docker with about 3 GB of memory to spare: about 1 GB for hyve's cluster and about 1.5 GB for
the CAPD cluster.

<Steps>

1. **Build hyve and its image.** See [Installation](/docs/installation) for the
   prerequisites.

   ```bash
   git clone -b v2 https://github.com/cbridges1/hyve.git && cd hyve
   task ui build image
   export PATH="$PWD:$PATH"
   ```

2. **Start local mode,** with the Docker and kubeadm providers CAPD clusters need:

   ```bash
   hyve local up --providers docker
   ```

   This creates a K3s container (`hyve-local`) on Docker's `kind` network, installs Cluster
   API, CAAPF, Fleet and hyve in it, and signs you in as its `admin` under the context
   `local`. It takes a few minutes the first time. A build from source uses the `hyve:dev`
   image you just built.

3. **Add a ClusterClass.** hyve's templates are built on Cluster API ClusterClasses. Download
   an example class for CAPD and apply it to the management cluster, through hyve:

   ```bash
   curl -LO https://cbridges1.github.io/hyve-website/examples/capd/clusterclass.yaml
   curl -LO https://cbridges1.github.io/hyve-website/examples/capd/kube-flannel.yml
   hyve cluster kubeconfig local > local.kubeconfig
   kubectl --kubeconfig local.kubeconfig apply -f clusterclass.yaml
   ```

   The class is `capd`, in `capi-clusters`, hyve's default template namespace.
   `hyve cluster kubeconfig local` prints a kubeconfig that reaches the management cluster through hyve as
   you; it holds no secret.

4. **Make a template.** A template sets the class's defaults for every cluster made from
   it. This one has one worker and expires its clusters at 20:00 UTC (put
   `CRON_TZ=<zone> ` in front of the schedule for your own time zone):

   ```bash
   hyve template create capd-small --class capd --workers 1 --schedule "0 20 * * *"
   ```

   CAPD installs no CNI, so deliver one to every cluster made from the template, and an app
   to show it works. Each is a Deployment aimed at the template:

   ```bash
   hyve deploy create flannel --path kube-flannel.yml --to template/capd-small
   hyve deploy create podinfo --helm podinfo \
       --repo https://stefanprodan.github.io/podinfo --version 6.7.1 -N podinfo \
       --to template/capd-small
   hyve deploy list
   ```

5. **Make an environment** for your clusters, and make it the default:

   ```bash
   hyve env create dev
   hyve env use dev
   ```

6. **Create a cluster from the template.** It waits until the cluster is up and registered
   with Fleet, a couple of minutes:

   ```bash
   hyve cluster create demo -t capd-small
   hyve cluster list
   ```

7. **See what was delivered.** Fleet puts the Deployments aimed at the template on the
   cluster:

   ```bash
   hyve cluster deployments demo
   ```

8. **Use the cluster.** `hyve cluster auth` adds it to your kubeconfig and switches kubectl to
   it. kubectl then reaches it through hyve, as you:

   ```bash
   hyve cluster auth demo
   kubectl get nodes
   kubectl -n podinfo get pods
   ```

   `hyve cluster kubeconfig demo > demo.kubeconfig` prints the same kubeconfig instead.

9. **Open the UI,** signed in:

   ```bash
   hyve ui
   ```

10. **Clean up.** Delete the cluster, then the local cluster:

    ```bash
    hyve cluster delete demo
    hyve local down
    ```

    `hyve local down` saves hyve's state first, so the next `hyve local up` brings back your
    templates and environments. `hyve local down --discard-state` forgets them.

</Steps>

<Aside type="tip">
Left alone, `demo` is deleted at the template's next 20:00 UTC. `hyve cluster create demo -t
capd-small --ttl 2h` sets its own expiry instead, and `--no-expiry` sets none.
</Aside>
