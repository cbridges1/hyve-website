## Overview

This guide walks you through creating your first Kubernetes cluster with Hyve using the module system. Hyve uses modules — versioned, self-contained packages — to provision clusters on any cloud provider.

<Tip>
  **Prefer to explore a working example first?** [hyve-sample-repo](https://github.com/cbridges1/hyve-sample-repo) is a complete, runnable state repository — modules, templates, workflows, and a cluster already wired together, using a fully local fake module so it works offline with zero cloud credentials. Clone it and run `hyve reconcile --path .` to see the whole lifecycle run immediately.
</Tip>

## Prerequisites

<AccordionGroup>
  <Accordion icon="cloud" title="Cloud provider CLI">
    Hyve does not bundle cloud SDKs. Your credentials stay in your environment. Install the CLI for whichever provider you're using:

    - **Civo**: Install the [Civo CLI](https://github.com/civo/cli) and authenticate with `civo apikey save my-token <token> && civo apikey use my-token`
    - **AWS**: Install the [AWS CLI](https://aws.amazon.com/cli/) and run `aws configure`
    - **GCP**: Install the [gcloud CLI](https://cloud.google.com/sdk/docs/install) and run `gcloud auth application-default login`
    - **Azure**: Install the [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli) and run `az login`
  </Accordion>

  <Accordion icon="folder" title="A directory for cluster state">
    Hyve reads and writes cluster YAML in a plain local directory — no database, no built-in git. A git repository is optional, only if you want version history and review (see [Environments](/docs/concepts/repositories)).
  </Accordion>

  <Accordion icon="code" title="Go 1.21+">
    Install [Go 1.21 or higher](https://golang.org/doc/install) to build and install Hyve.
  </Accordion>
</AccordionGroup>

## Step 1 — Install Hyve

<Steps>
  <Step title="Install with Go">
    ```bash
    go install github.com/cbridges1/hyve@latest
    ```

    This installs the `hyve` binary to your `$GOPATH/bin`. Ensure `$(go env GOPATH)/bin` is in your `PATH`.
  </Step>

  <Step title="Verify installation">
    ```bash
    hyve --help
    ```
  </Step>
</Steps>

## Step 2 — Point hyve at a directory

Hyve has no built-in git functionality — it just reads and writes plain files in whatever directory you register. If you want it version-controlled, clone it yourself first (using your own git credentials, however you normally authenticate — SSH key, token, whatever your provider needs):

```bash
git clone https://github.com/your-org/hyve-state.git
hyve env create production --path ./hyve-state
```

Don't want git at all? Skip the clone — `hyve env create --path` works against any plain local directory:

```bash
mkdir my-hyve-config && hyve env create production --path ./my-hyve-config
```

Either way, `hyve env create` registers it *and* makes it active immediately — every command below operates against it. See [Environments](/docs/concepts/repositories).

## Step 3 — Install a module

Modules implement cluster operations for a specific cloud provider. Install a module and lock it in `hyve.lock`:

<Tabs>
  <Tab title="Civo">
    ```bash
    hyve module add github.com/hyve-modules/civo@v1.0.0
    ```
  </Tab>

  <Tab title="AWS EKS">
    ```bash
    hyve module add github.com/hyve-modules/eks@v1.0.0
    ```
  </Tab>

  <Tab title="GCP GKE">
    ```bash
    hyve module add github.com/hyve-modules/gke@v1.0.0
    ```
  </Tab>

  <Tab title="Azure AKS">
    ```bash
    hyve module add github.com/hyve-modules/aks@v1.0.0
    ```
  </Tab>
</Tabs>

## Step 4 — Create a template

Templates define the shape of a cluster — driver, region, and module-specific params. Use `--set KEY=VALUE` to supply params:

<Tabs>
  <Tab title="Civo">
    ```bash
    hyve template create my-civo-template \
      --driver github.com/hyve-modules/civo \
      --driver-version v1.0.0 \
      --region PHX1 \
      --set node_size=g4s.kube.medium \
      --set node_count=3
    ```

    Civo credentials are read automatically from the Civo CLI (`~/.civo.json`) or the `CIVO_TOKEN` environment variable.
  </Tab>

  <Tab title="AWS EKS">
    ```bash
    hyve template create my-eks-template \
      --driver github.com/hyve-modules/eks \
      --driver-version v1.0.0 \
      --region us-east-1 \
      --set vpc_id=vpc-0abc123456789 \
      --set eks_role_arn=arn:aws:iam::123456789012:role/eks-role \
      --set node_role_arn=arn:aws:iam::123456789012:role/node-role \
      --set instance_type=t3.medium \
      --set node_count=3
    ```

    AWS credentials are read from `~/.aws/credentials` or environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`).
  </Tab>

  <Tab title="GCP GKE">
    ```bash
    hyve template create my-gke-template \
      --driver github.com/hyve-modules/gke \
      --driver-version v1.0.0 \
      --region us-central1 \
      --set project_id=my-gcp-project \
      --set machine_type=e2-standard-4 \
      --set node_count=3
    ```

    GCP credentials are read from Application Default Credentials (`gcloud auth application-default login`).
  </Tab>

  <Tab title="Azure AKS">
    ```bash
    hyve template create my-aks-template \
      --driver github.com/hyve-modules/aks \
      --driver-version v1.0.0 \
      --region eastus \
      --set subscription_id=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
      --set resource_group=my-rg \
      --set vm_size=Standard_DS2_v2 \
      --set node_count=3
    ```

    Azure credentials are read from the Azure CLI session (`az login`) or service principal environment variables.
  </Tab>
</Tabs>

## Step 5 — Create a cluster

Create a cluster from the template — this generates the cluster definition YAML and provisions the cluster:

```bash
hyve cluster create my-cluster --template my-civo-template
```

This writes `clusters/my-cluster.yaml` to your Git repository, commits it, and runs reconciliation to provision the cluster.

## Step 6 — Authenticate (get kubeconfig)

Once the cluster is ready, run the module's auth operation to merge the cluster into `~/.kube/config`:

```bash
hyve cluster auth my-cluster
```

Then use the cluster:

```bash
kubectl config use-context my-cluster
kubectl get nodes
```

## Step 7 — Reconcile

Going forward, any change to a cluster definition (committed to Git) is applied by running:

```bash
hyve reconcile
```

This reads all cluster YAMLs from Git, calls the appropriate module, and reconciles desired state with actual state.

<Note>
  For CI/CD pipelines, set `reconcile.mode: cicd` in `hyve.yaml` at your repo root. Then your pipeline calls `hyve reconcile --path .` after each push to apply changes.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Module not found after add">
    Run `hyve module validate` to confirm all template modules are locked and cached:

    ```bash
    hyve module validate
    ```
  </Accordion>

  <Accordion title="Credentials not found">
    Modules read credentials from environment variables or the cloud CLI's config files. Ensure the relevant CLI is authenticated before running Hyve:

    ```bash
    # Civo
    civo apikey list

    # AWS
    aws sts get-caller-identity

    # GCP
    gcloud auth application-default print-access-token

    # Azure
    az account show
    ```
  </Accordion>

  <Accordion title="No environment configured">
    You need to register one first:

    ```bash
    hyve env create my-project --path ./my-hyve-config
    ```
  </Accordion>

  <Accordion title="Cloning a private repository fails">
    That's your own `git clone` step, before `hyve env create` — authenticate with `git` however you normally do (SSH key, a credential helper, a token in the URL). Hyve itself never touches the clone or its credentials.
  </Accordion>
</AccordionGroup>
