Manages hyve.io User objects on the signed-in hyve host. Users sign in with
a username and password; Kubernetes sees them as hyve:&lt;username&gt;, in groups
hyve:&lt;group&gt;. Grant them access with RBAC on those names.

Everything goes through the host's /k8s/clusters/local as you, so it needs
the matching RBAC on users.hyve.io (and update on users/password to set
someone else's password).

```text
  hyve user [command]
```

**Flags**

```text
  -h, --help   help for user
```

### hyve user create

Creates a user. With --invite, the host emails them a link and code to set
their own password (it works for 7 days; 'hyve user invite' sends another).
Otherwise you choose their initial password, which they change at first
sign-in unless --no-password-change, and they're emailed that the account
exists.

An email address is required: it's where password resets and account
emails go.

With --service, it's a user for CI and scripts: no password and no email.
It signs in with API tokens ('hyve user token create --user NAME') or as a
trusted CI job ('hyve user trust add NAME ...').

```text
  hyve user create NAME (--email ADDRESS | --service) [flags]
```

Aliases: `create, add`

**Examples**

```text
  hyve user create alice --email alice@example.com --invite
  hyve user create ci --service --group deployers
```

**Flags**

```text
      --display-name string   name shown in the UI
      --email string          address for password resets and account emails (required)
      --group strings         group to add the user to (repeatable)
  -h, --help                  help for create
      --invite                email them a link to set their own password instead of choosing one
      --no-password-change    don't make the user change the password at first sign-in
      --password-stdin        read the initial password from stdin
      --server string         saved server to use (default: the one last signed in to)
      --service               a user for CI and scripts: no password or email; it signs in with API tokens or as trusted CI
```

### hyve user passwd

Without NAME, changes your own password (asking for the current one) and
signs out your other sessions. With NAME, sets that user's password, which
needs update on users/password, and signs them out everywhere.

```text

```

### hyve user token

An API token signs in as a user without a password, for scripts and CI:
'hyve login URL --token-stdin', or HYVE_URL and HYVE_TOKEN in the
environment. It acts as that user, with that user's access, and lasts until
it expires (at most a year) or is revoked. Changing the user's password
doesn't revoke it; disabling the user stops it.

You can manage your own tokens. Another user's (a CI user's) take the right
to the users/tokens subresource of that User: admins have it. A token can't
make tokens, so one that leaks can't outlive its expiry.

A CI job can often sign in with no token at all: see 'hyve user trust'.

```text
  hyve user token [command]
```

**Flags**

```text
  -h, --help   help for token
```

#### hyve user token create

Make an API token; it's printed once, on stdout

```text
  hyve user token create NAME [flags]
```

**Examples**

```text
  hyve user token create laptop --expires 30d
  hyve user token create github --user ci --expires 90d --description "web's release pipeline"
```

**Flags**

```text
      --description string   what it's for
      --expires string       how long it lasts: 30d, 1y (the most), 720h (default "90d")
  -h, --help                 help for create
      --server string        saved server to use (default: the one last signed in to)
      --user string          the user it signs in as (default: you)
```

### hyve user trust

CI systems give each job an ID token: a short-lived, signed statement of
which repository, branch and workflow it is. A user that trusts a CI
system's jobs lets them sign in as it with that token ('hyve login URL
--username USER --github-actions', or --id-token-env), for an hour. The
pipeline keeps no password or API token.

An entry names the CI system's issuer and the claims a job's token must
have. One claim must pin the repository or project (repository, sub,
project_path...); a '*' in a value matches anything. The job's token must
be for the entry's audience ("hyve" unless --audience says).

Editing a user's trusted CI takes the right to update that User: admins
have it.

```text
  hyve user trust [command]
```

**Flags**

```text
  -h, --help   help for trust
```

#### hyve user trust add

Trust a CI system's jobs to sign in as USER

```text
  hyve user trust add USER NAME (--github OWNER/REPO | --gitlab GROUP/PROJECT | --issuer URL --claim K=V...) [flags]
```

**Examples**

```text
  hyve user trust add ci web-releases --github org/web --claim ref='refs/tags/*'
  hyve user trust add ci web-main --github org/web --claim ref=refs/heads/main --claim environment=production
  hyve user trust add ci infra --gitlab platform/infra --claim ref_protected=true
  hyve user trust add ci builds --issuer https://agent.buildkite.com --claim organization_slug=acme --claim pipeline_slug=web
```

**Flags**

```text
      --audience string     the audience the job's token must be for (default "hyve")
      --claim stringArray   a claim the job's token must have, KEY=VALUE; '*' matches anything (repeatable)
      --github string       GitHub Actions jobs of this repository (OWNER/REPO)
      --gitlab string       GitLab CI jobs (gitlab.com) of this project (GROUP/PROJECT)
  -h, --help                help for add
      --issuer string       another CI system's OIDC issuer URL
      --server string       saved server to use (default: the one last signed in to)
```
