### hyve cluster adopt

Creates a cluster from a template that sets 'adopt', whose ClusterClass's
provider takes over the existing cluster with this ID (a Civo cluster's
ID, for cluster-api-provider-civo) instead of creating one. NAME needn't
be the cluster's own name. From then on hyve manages it like any other:
scaling, upgrades and deletion go through the provider.

The template's adopt.variables replace its variables on an adopted
cluster, and adopt.unset leaves some unset: usually so the provider keeps
the cluster when the hyve cluster is deleted (deletionPolicy: Retain) and
leaves its size alone (unset: [nodeCount]).
An adopted cluster takes no expiry schedule; --ttl gives it one.

Give --version as the cluster's Kubernetes version: the template's is
used otherwise. For a cluster with no provider that adopts, use
'hyve cluster import'.

```text
  hyve cluster adopt NAME --template TEMPLATE --id ID [flags]
```

**Examples**

```text
  hyve cluster adopt web -t civo -e prod --id 7f3c0d6e-0b5d-4b51-9b8a-1c2d3e4f5a6b --set region=NYC1 --version v1.33.0
```

**Flags**

```text
      --dry-run             print the Cluster instead of creating it
  -h, --help                help for adopt
      --id string           the existing cluster's ID at its provider
      --label stringArray   label key=value on the Cluster (repeatable)
      --no-wait             return once the Cluster object is created
      --set stringArray     ClusterClass variable name=value (repeatable), e.g. its region
  -t, --template string     ClusterTemplate with adopt set (in the template namespace)
      --timeout duration    how long to wait (default 15m0s)
      --ttl duration        expire (delete) the cluster this long from now
      --version string      the cluster's Kubernetes version (default: the template's)
```

### hyve cluster auth

Adds the kubeconfig 'hyve cluster kubeconfig' prints to your kubeconfig
($KUBECONFIG, or ~/.kube/config) and makes it the current context, so
kubectl reaches the cluster through the signed-in server's proxy, as you.
Running it again refreshes the entry. Like that kubeconfig, it holds no
secret: the credential is 'hyve token'. NAME local is the host cluster.

```text
  hyve cluster auth NAME [flags]
```

**Examples**

```text
  hyve cluster auth demo
  hyve cluster auth local
  hyve cluster auth web -e prod
```

**Flags**

```text
  -h, --help   help for auth
```

### hyve cluster create

Creates a Cluster API Cluster in the environment. With --template it's
labelled with the template, and filled in from it and its ClusterClass:
the same thing hyve-controller does for a labelled Cluster created any
other way (kubectl, GitOps, the UI). What's deployed to the template (its
group in Fleet) then reaches it.

--set sets ClusterClass variables; values are parsed as JSON when they are
valid JSON (numbers, lists, objects), otherwise used as strings. A variable
the template locks can't be changed.

By default waits until the cluster is ACTIVE and registered with Fleet.

```text
  hyve cluster create NAME (--template TEMPLATE | --class CLASS) [flags]
```

**Examples**

```text
  hyve cluster create demo --template capd-small --ttl 4h
  hyve cluster create web --template civo --set region=LON1 --workers 3 -e prod
  hyve cluster create demo --class capd --class-namespace capi-clusters
```

**Flags**

```text
      --class string             ClusterClass to build from, without a template
      --class-namespace string   the ClusterClass's namespace with --class (default: the environment)
      --control-plane int        control-plane replicas (default: 1 for a machine-based control plane, none for a managed one)
      --dry-run                  print the Cluster instead of creating it
  -h, --help                     help for create
      --label stringArray        label key=value on the Cluster (repeatable; Fleet sees it through CAAPF)
      --no-expiry                don't expire the cluster, whatever the template's schedule
      --no-wait                  return once the Cluster object is created
      --secrets-env              create the Secrets the Deployments aimed at the template copy, from environment variables: Secret my-secret from MY_SECRET (a JSON object of keys, or one value under key "value")
      --set stringArray          ClusterClass variable name=value (repeatable)
  -t, --template string          ClusterTemplate to build from (in the template namespace)
      --timeout duration         how long to wait (default 30m0s)
      --ttl duration             expire the cluster this long after creation (replaces the template's schedule)
      --version string           Kubernetes version (default: the template's, or the class's hyve.io/default-version)
      --worker-class string      worker class (default: the template's, or the class's first)
      --worker-type string       machineDeployment or machinePool
      --workers int              worker replicas (default 1)
```

### hyve cluster import

Imports a cluster hyve didn't create (EKS, GKE, AKS, on-prem, kind...),
reached with a kubeconfig you have: your current context unless
--from-kubeconfig or --from-context say otherwise.

On the cluster, a ServiceAccount (kube-system/hyve-import, cluster-admin)
gives hyve credentials of its own, so a kubeconfig that runs a command
(aws, gcloud) works too. In the environment, a Cluster API Cluster points
at it; Fleet registers it, and access, Deployments, kubeconfigs and the
Explorer work as for any cluster. --template puts it in a template's group,
so it gets what's deployed to the template (not its variables, version or
expiry).

hyve never creates, scales, upgrades or deletes an imported cluster.
'hyve cluster delete' detaches it: it removes hyve's and Fleet's agents and
hyve's ServiceAccount from the cluster, and leaves the rest, including what
Fleet deployed.

hyve's host must reach the cluster's API server. When it reaches it at
another address than you do (a private DNS name, host.docker.internal),
give it with --api-server.

```text
  hyve cluster import NAME [--from-kubeconfig FILE] [--from-context CONTEXT] [flags]
```

**Examples**

```text
  hyve cluster import legacy-eks -e prod --from-context arn:aws:eks:us-east-1:123456789012:cluster/legacy
  hyve cluster import lab --from-kubeconfig lab.yaml --template base
  hyve cluster import kind-dev --from-context kind-dev --api-server https://host.docker.internal:6443
```

**Flags**

```text
      --api-server string        the API server's URL as hyve's host reaches it (default: the kubeconfig's)
      --from-context string      context in it (default: its current one)
      --from-kubeconfig string   kubeconfig that reaches the cluster (default: $KUBECONFIG or ~/.kube/config)
  -h, --help                     help for import
      --label stringArray        label key=value on the Cluster (repeatable; Fleet sees it through CAAPF)
      --no-wait                  return once the objects are created
  -t, --template string          put the cluster in this template's group, so it gets what's deployed to the template
      --timeout duration         how long to wait (default 10m0s)
```

### hyve cluster kubeconfig

Prints a kubeconfig for &lt;url&gt;/k8s/clusters/&lt;id&gt; on the signed-in server:
the same proxy and the same sign-in as the management cluster, so kubectl
runs under your own permissions. It holds no secret; it runs 'hyve token'.
The cluster's admin credentials are never handed out. 'hyve cluster auth'
adds it to your kubeconfig instead. NAME local is the host cluster.

```text
  hyve cluster kubeconfig NAME [flags]
```

**Flags**

```text
  -h, --help   help for kubeconfig
```

### hyve cluster upgrade

Sets the cluster's Kubernetes version (spec.topology.version). Cluster API
rolls the control plane to it, then the workers, one machine at a time.
The ClusterClass's providers must support the version; Cluster API refuses
skipping a minor version or going back. A template that locks
kubernetesVersion keeps its clusters at its own.

```text
  hyve cluster upgrade NAME --version VERSION [flags]
```

**Examples**

```text
  hyve cluster upgrade demo --version v1.35.2
```

**Flags**

```text
  -h, --help             help for upgrade
      --version string   the Kubernetes version, e.g. v1.35.2
```
