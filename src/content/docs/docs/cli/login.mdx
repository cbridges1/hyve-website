`hyve env login`/`hyve env logout`/`hyve env whoami` authenticate the CLI against a deployed cluster-mode API — see [Cluster Mode](/docs/concepts/cluster-mode). Local/directory-based work never needs any of these.

<Note>
  **A login is one global, machine-wide credential — like `gh auth login` — not scoped to whichever [environment](/docs/concepts/repositories) is active.** Switching environments never logs you out; logging in or out never changes which environment is active, except that the very first login on a machine with no environment registered yet also activates the one it creates.
</Note>

## Commands

### hyve env login

```bash
hyve env login [--api-url <url>] [--org <name>] [--username <user>] [--password <password>] [--ca-cert <path>]
```

<ParamField path="--api-url" type="string">
  The cluster-mode API to authenticate against. Defaults to the current environment's `--api-url`, if it has one. If the URL isn't already registered as an environment, one is registered automatically (named from the URL's host, deduplicated on collision) — so a bare `hyve env login --api-url ...` is enough to both authenticate and make that cluster visible in `hyve env list` afterward.
</ParamField>

<ParamField path="--org" type="string">
  Which [organization](/docs/concepts/multi-tenancy) to log into, on a shared, multi-tenant install. Resolved server-side to that organization's real namespace — omit entirely for the control-plane/`superadmin` tier, which has no tenant namespace of its own.
</ParamField>

<ParamField path="--username" type="string">
  Local account username. Omit to be prompted.
</ParamField>

<ParamField path="--password" type="string">
  Local account password. Omit to be prompted without echo — scripting/CI is the only real reason to pass this as a flag instead.
</ParamField>

<ParamField path="--ca-cert" type="string">
  Path to a PEM-encoded CA certificate to trust in addition to the system trust store — for an API whose TLS certificate isn't publicly trusted (a self-signed CA behind a bare IP/nip.io address with no real domain). Stored on the registered environment once login succeeds, so later commands against it (`hyve cluster auth`, `hyve env whoami`, ...) trust it too without repeating the flag.
</ParamField>

```bash
hyve env login --api-url https://hyve-api.example.com --org acme
# Username: alice
# Password: ********
# ✅ Logged in as alice against https://hyve-api.example.com (session expires ...)
```

### hyve env whoami

Confirm who you're authenticated as, and where.

```bash
hyve env whoami
```

### hyve env logout

Revoke the current session and clear the locally cached credential.

```bash
hyve env logout
```

## Session model

<Info>
  Two credentials, not one — modeled after a stateful-session-plus-fast-cache pattern rather than classic independent OAuth2 access+refresh tokens.
</Info>

- **Access token** — short-lived (~30 minutes), used on every API call, verified locally with no round trip to the cluster on the hot path.
- **Session token** — long-lived (~30 days), kept only to silently mint a fresh access token when the cached one expires — no password re-entry needed for routine use, which is what makes unattended use (a cron job, a CI pipeline already logged in) practical.

The session itself is a real, revocable row in hyve-api's own datastore — see [Access Control](/docs/concepts/access-control) — and `hyve env logout` revokes it immediately server-side, not just locally.

<Warning>
  Your role (admin / read-only / custom) is resolved fresh from your own access binding on every request, not baked into the token — a role change by an admin takes effect on your very next command, not your next login.
</Warning>

<Note>
  If a cluster-mode command seems to be talking to the wrong server even after `hyve env use` switched you to a local/different environment, check `hyve env whoami` first — a still-active session takes precedence over the current environment for any cluster-mode-aware command, by design. `hyve env logout` first if that's not what you want.
</Note>
