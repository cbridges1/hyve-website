hyve has no secret store. A [Deployment](/docs/concepts/deployments) that needs credentials (a
DNS token, a registry login) names plain Kubernetes Secrets in its own namespace on the
management cluster, and Fleet copies them to each cluster it reaches, with Fleet's own
`downstreamResources`.

How those Secrets get filled is up to you: `hyve deploy secret create`, `kubectl`, or an operator such
as External Secrets, Infisical's or sealed-secrets. hyve only checks that they exist.

## Naming the Secrets a Deployment needs

```bash
hyve deploy create external-dns --helm external-dns \
    --repo https://kubernetes-sigs.github.io/external-dns/ --version 1.19.0 \
    -N external-dns --secret cloudflare-dns --to template/civo-small
```

```yaml
# the HelmOp that makes
spec:
  downstreamResources:
    - kind: Secret
      name: cloudflare-dns
```

In the UI it's **Secrets to copy** on the Deployment's form. A git source can't list them on
the GitRepo: Fleet reads `downstreamResources` from the repo's own `fleet.yaml` for those.

Fleet copies a Secret only while it exists. `hyve deploy secret list` and the Deployment's page show
which are missing.

## Which namespace

The Secret goes in the namespace of what names it:

| Who reads it | Namespace |
|---|---|
| A Deployment | The Deployment's own: the template namespace (`capi-clusters` by default), an environment, or `fleet-local`. |
| A Cluster API provider (a Civo API key, SSH credentials for a host, a cloud key the class names) | The cluster's environment. Providers look only in the cluster's own namespace, so put the Secret in each environment you create clusters in. |

Credentials a provider reads for itself, in its own configuration (for example CAPG's
`GCP_B64ENCODED_CREDENTIALS`), aren't Secrets you create here: they're provider variables. See
[Providers](/docs/concepts/providers).

## Commands

```bash
# create one, values from the environment or files, never from the command line
CF_TOKEN=... hyve deploy secret create cloudflare-dns --from-env api-token=CF_TOKEN
CIVO_TOKEN=... hyve deploy secret create civo-credentials -n dev --from-env token=CIVO_TOKEN
hyve deploy secret create registry --type kubernetes.io/dockerconfigjson \
    --from-file .dockerconfigjson=$HOME/.docker/config.json

# change keys; clusters get the change the next time Fleet copies it
CF_TOKEN=... hyve deploy secret set cloudflare-dns --from-env api-token=CF_TOKEN
hyve deploy secret set registry --remove old-key

hyve deploy secret list            # what's needed, whether it exists, and its keys
hyve deploy secret show cloudflare-dns
hyve deploy secret delete cloudflare-dns
```

Without `-n`/`--namespace`, `create`, `set`, `show` and `delete` work in the template namespace.

What each command prints:

| Command | Prints |
|---|---|
| `hyve deploy secret list` | The Secrets each Deployment has Fleet copy, whether each exists in the Deployment's namespace, and its keys. Names only: it never reads values. |
| `hyve deploy secret show NAME` | The Secret's type, labels and keys. Values stay hidden. |
| `hyve deploy secret show NAME --reveal` | The values too. |
| `create`, `set` | Nothing of the values. |

<Aside type="caution">
`--from-literal` puts the value in your shell history. Prefer `--from-env` or `--from-file` for
real secrets.
</Aside>

`hyve deploy secret` runs as you, so it needs RBAC on Secrets in that namespace. Environment members
don't have it.

`hyve cluster create --secrets-env` creates the Secrets that the template namespace's
Deployments reaching the template's clusters need, from environment variables, in the template
namespace: Secret `my-secret` from `MY_SECRET`, holding a
JSON object of keys or a single value under the key `value`. It's meant for CI.

## In the UI

A Deployment's page lists its Secrets: whether each exists, its keys, and buttons to create or
change them in the Deployment's namespace. A cluster's **Deployments** tab has a Secrets section
too: the Secret its Cluster API provider reads (`credentialsRef` on its infrastructure cluster,
as the Civo and Unraid providers have), and the Secrets its environment's Deployments copy. Both
include the Secrets a git source's `fleet.yaml` names, read from the bundles Fleet made from
it.

Any other Secret, on the management cluster or a cluster's own, is in the
[Explorer](/docs/guides/web-ui#the-explorer), which shows values decoded and creates Secrets with
the same form.
