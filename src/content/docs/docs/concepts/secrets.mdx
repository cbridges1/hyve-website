hyve has no secret store. A resource that needs credentials (a DNS token, a registry login)
names plain Kubernetes Secrets in its owner's namespace on the management cluster, and Fleet
copies them to each cluster the resource goes to, with Fleet's own `downstreamResources`.

How those Secrets get filled is up to you: `hyve secrets create`, `kubectl`, or an operator such
as External Secrets, Infisical's or sealed-secrets. hyve only checks that they exist.

## Naming the Secrets a resource needs

```yaml
# a template entry, a shared Resource or a ClusterResource
- name: external-dns
  namespace: external-dns
  secrets: [cloudflare-dns]
  helmOp:
    helm:
      repo: https://kubernetes-sigs.github.io/external-dns/
      chart: external-dns
      version: 1.19.0
```

hyve-controller adds each name to the Fleet object's `downstreamResources` as a `Secret`. A
template entry that uses a shared Resource gets the shared Resource's Secrets and its own.

A `gitRepo` resource can't list `secrets`: Fleet reads `downstreamResources` from the repo's own
`fleet.yaml` for those.

While a named Secret doesn't exist, the template's or `ClusterResource`'s `Ready` condition is
`False` with reason `SecretsMissing`, and `status.missingSecrets` lists them.

## Which namespace

The Secret goes in the namespace of what names it:

| Who reads it | Namespace |
|---|---|
| A template's resources | The template namespace (`capi-clusters` by default). |
| One cluster's extras (`ClusterResource`s) | The cluster's environment. |
| A Cluster API provider (a Civo API key, SSH credentials for a host, a cloud key the class names) | The cluster's environment. Providers look only in the cluster's own namespace, so put the Secret in each environment you create clusters in. |

Credentials a provider reads for itself, in its own configuration (for example CAPG's
`GCP_B64ENCODED_CREDENTIALS`), aren't Secrets you create here: they're provider variables. See
[Providers](/docs/concepts/providers).

## Commands

```bash
# create one, values from the environment or files, never from the command line
CF_TOKEN=... hyve secrets create cloudflare-dns --from-env api-token=CF_TOKEN
CIVO_TOKEN=... hyve secrets create civo-credentials -n dev --from-env token=CIVO_TOKEN
hyve secrets create registry --type kubernetes.io/dockerconfigjson \
    --from-file .dockerconfigjson=$HOME/.docker/config.json

# change keys; clusters get the change the next time Fleet copies it
CF_TOKEN=... hyve secrets set cloudflare-dns --from-env api-token=CF_TOKEN
hyve secrets set registry --remove old-key

hyve secrets list            # what's needed, whether it exists, and its keys
hyve secrets show cloudflare-dns
hyve secrets delete cloudflare-dns
```

Without `-n`/`--namespace`, `create`, `set`, `show` and `delete` work in the template namespace.

What each command prints:

| Command | Prints |
|---|---|
| `hyve secrets list` | The Secrets template resources (template namespace) and cluster extras (environment) have Fleet copy, whether each exists, and its keys. Names only: it never reads values. |
| `hyve secrets show NAME` | The Secret's type, labels and keys. Values stay hidden. |
| `hyve secrets show NAME --reveal` | The values too. |
| `create`, `set` | Nothing of the values. |

<Aside type="caution">
`--from-literal` puts the value in your shell history. Prefer `--from-env` or `--from-file` for
real secrets.
</Aside>

`hyve secrets` runs as you, so it needs RBAC on Secrets in that namespace. Environment members
don't have it.

`hyve cluster create --secrets-env` creates the Secrets a template's resources need from
environment variables, in the template namespace: Secret `my-secret` from `MY_SECRET`, holding a
JSON object of keys or a single value under the key `value`. It's meant for CI.

## In the UI

A template's page has a **Secrets** section: the Secrets its resources copy, whether each
exists, its keys, and buttons to create or change them in the template namespace. A cluster's
**Resources** tab has the same for its environment: what its extras copy, and the Secret its
Cluster API provider reads (`credentialsRef` on its infrastructure cluster, as the Civo and
Unraid providers have). Both include the Secrets a git resource's `fleet.yaml` names, read from
the bundles Fleet made from it.

Any other Secret, on the management cluster or a cluster's own, is in the
[Explorer](/docs/guides/web-ui#the-explorer), which shows values decoded and creates Secrets with
the same form.
