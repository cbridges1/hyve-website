## Overview

Templates in Hyve are reusable cluster configurations that combine a driver/region/params with automated post-deployment workflows. They enable consistent cluster creation with standardized configurations and deployment processes.

## Template Structure

Templates are YAML files that define a driver, region, params, and optional lifecycle workflows:

```yaml
apiVersion: hyve.io/v1alpha1
kind: Template
metadata:
  name: prod-template
  description: Production cluster template with monitoring
spec:
  driver:
    source: github.com/hyve-modules/civo
    version: v1.0.0
  region: NYC1
  params:
    node_size: g4s.kube.large
    node_count: "3"
  schedule: "0 20 * * 5"   # optional: auto-expire clusters every Friday at 20:00
  workflows:
    onCreate:
      - setup-monitoring
      - deploy-base-apps
    onDelete:
      - backup-data
```

### Metadata

<ParamField path="metadata.name" type="string" required>
  Unique template identifier
</ParamField>

<ParamField path="metadata.description" type="string">
  Human-readable description of the template
</ParamField>

### Spec

<ParamField path="spec.driver.source" type="string" required>
  Module source string (e.g. `github.com/hyve-modules/civo`)
</ParamField>

<ParamField path="spec.driver.version" type="string" required>
  Module version. Must be locked in `hyve.lock`.
</ParamField>

<ParamField path="spec.region" type="string">
  Passed to the module as part of cluster context. Can be overridden at cluster-creation time with `--region`.
</ParamField>

<ParamField path="spec.params" type="object">
  Arbitrary key/value pairs, entirely module-specific — there's no hyve-defined schema of provider fields. Check the module's own `module.yaml`/README for what it expects. Injected as `HYVE_PARAM_<KEY>` env vars for every module operation; values can be overridden at cluster-creation time with `--set`.
</ParamField>

<ParamField path="spec.workflows.beforeCreate" type="array">
  List of workflow names to execute before the cluster is created. No kubeconfig — the cluster does not exist yet. Output variables in `HYVE_KEY=value` format are captured and applied to the cluster definition.
</ParamField>

<ParamField path="spec.workflows.onCreate" type="array">
  List of workflow names to execute after cluster creation, before `spec.resources` applies for this cycle. Kubeconfig is available.
</ParamField>

<ParamField path="spec.workflows.afterCreate" type="array">
  List of workflow names to execute after cluster creation, after `spec.resources` has applied for this cycle. Kubeconfig is available. Use instead of `onCreate` when a workflow depends on something `spec.resources` creates.
</ParamField>

<ParamField path="spec.workflows.onDelete" type="array">
  List of workflow names to execute before cluster deletion. Cluster is still running; kubeconfig is available.
</ParamField>

<ParamField path="spec.workflows.afterDelete" type="array">
  List of workflow names to execute after the cluster has been deleted. No kubeconfig — the cluster no longer exists. Use to tear down infrastructure provisioned by `beforeCreate`.
</ParamField>

<ParamField path="spec.workflows.preReconcile" type="array">
  List of workflow names to execute at the start of every reconcile loop for this cluster, before any create/update/delete decisions are made.
</ParamField>

<ParamField path="spec.resources" type="array">
  Kubernetes manifests hyve owns, drift-checks, and re-applies — see [Resources](/docs/concepts/resources).
</ParamField>

<ParamField path="spec.lockParams" type="string[]">
  Names of params whose values, once a cluster is created from this template, get hashed and recorded — not a permission lock. This is what `hyve cluster adopt`'s drift detection uses to tell "set intentionally at creation" apart from "looks like drift," for exactly the params listed here.

  ```yaml
  spec:
    lockParams: [node_size, node_count]
  ```
</ParamField>

## Creating Templates

```bash
hyve template create prod-template \
  --driver github.com/hyve-modules/civo --driver-version v1.0.0 \
  --region NYC1 \
  --set node_size=g4s.kube.large --set node_count=3
```

<Note>
  `hyve template create` only sets `driver`/`region`/`params` (via `--set`). Lifecycle workflows and `schedule` aren't CLI flags — add them by editing the generated YAML afterward, or write the file directly:

  ```bash
  cat > templates/prod-template.yaml <<EOF
  apiVersion: hyve.io/v1alpha1
  kind: Template
  metadata:
    name: prod-template
    description: Production cluster with 3 large nodes
  spec:
    driver:
      source: github.com/hyve-modules/civo
      version: v1.0.0
    region: NYC1
    params:
      node_size: g4s.kube.large
      node_count: "3"
    workflows:
      onCreate:
        - setup-monitoring
        - deploy-base-apps
      onDelete:
        - backup-data
  EOF
  ```

  If your environment directory is git-backed (optional — see [Version Control](/docs/concepts/gitops)), commit it like any other file.
</Note>

## Executing Templates

```bash
hyve cluster create my-prod-cluster --template prod-template
```

<Steps>
  <Step title="Load template">
    Read the template YAML from the active environment.
  </Step>
  <Step title="Generate + provision">
    Generate the cluster definition, then run reconciliation: `beforeCreate` → provision via the driver module → wait for `ACTIVE`.
  </Step>
  <Step title="Merge kubeconfig">
    Merge the new cluster's kubeconfig into `~/.kube/config`.
  </Step>
  <Step title="Run onCreate / afterCreate">
    Run `onCreate` workflows, apply `spec.resources`, then run `afterCreate` workflows.
  </Step>
</Steps>

`onDelete`/`afterDelete` run later, when the cluster is deleted.

### Lifecycle Events

| Event | When It Runs | Kubeconfig | Use Cases |
|-------|--------------|------------|-----------|
| `beforeCreate` | Before the cluster is provisioned | No | Provision VPC, IAM roles, DNS zones |
| `onCreate` | After cluster is ready, before `spec.resources` applies | Yes | Setup monitoring, deploy apps, configure ingress |
| `afterCreate` | After cluster is ready, after `spec.resources` has applied | Yes | Create a Secret a resource-managed Deployment references, DNS pointing at a now-deployed app |
| `onDelete` | Before cluster deletion | Yes | Backup data, drain workloads, notify teams |
| `afterDelete` | After the cluster is deleted | No | Tear down VPC, IAM roles, DNS zones |

<Note>
  Workflows referenced in a template must exist in the same environment's `workflows/` directory (or as real `Workflow` objects, in cluster mode).
</Note>

## Managing Templates

```bash
hyve template list
hyve template show prod-template
hyve template delete old-template
```

<Note>
  Deleting a template doesn't affect clusters already created from it — a cluster's YAML is a full, independent copy of what the template generated at creation time, not a live reference back to it.
</Note>

## Use Cases

### Rapid Environment Creation

```bash
hyve cluster create prod-cluster-01 --template prod-template
hyve cluster create prod-cluster-02 --template prod-template
# Both identical: same driver, region, params, and workflows
```

### Multi-Region Deployment

```bash
hyve cluster create us-east-prod --template prod-template --region NYC1
hyve cluster create us-west-prod --template prod-template --region PHX1
hyve cluster create eu-prod --template prod-template --region FRA1
```

### Testing Infrastructure Changes

```bash
hyve env use development
hyve cluster create test-new-config --template prod-template

# If successful
hyve env use production
hyve cluster create prod-new-cluster --template prod-template
```

## Best Practices

<AccordionGroup>
  <Accordion title="Use descriptive names">
    ```yaml
    # Good
    metadata:
      name: production-ha-template
      description: Production HA cluster with monitoring and logging

    # Avoid
    metadata:
      name: template1
    ```
  </Accordion>

  <Accordion title="Include essential workflows">
    ```yaml
    workflows:
      onCreate:
        - setup-monitoring
        - configure-security
        - setup-backup
        - deploy-core-services
      onDelete:
        - export-logs
        - backup-final-state
    ```
  </Accordion>

  <Accordion title="Test templates in development first">
    ```bash
    hyve env use development
    hyve cluster create test-cluster --template new-template
    # Verify workflows run successfully, then:
    hyve env use production
    hyve cluster create prod-cluster --template new-template
    ```
  </Accordion>

  <Accordion title="Version control templates (optional)">
    If your environment directory is git-backed, commit template changes with descriptive messages — tags work fine too for marking a template version you want to be able to return to:

    ```bash
    git commit -am "Update production template: add cert-manager to onCreate"
    git tag -a prod-template-v1.1 -m "Add cert-manager"
    ```
  </Accordion>
</AccordionGroup>
