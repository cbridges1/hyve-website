A **ClusterTemplate** (`hyve.io/v1alpha1`) is what people pick when they make a cluster. It
sits on top of a Cluster API [ClusterClass](https://cluster-api.sigs.k8s.io/tasks/experimental-features/cluster-class/)
and adds what a ClusterClass doesn't have:

- **Defaults:** the Kubernetes version, control-plane and worker replicas, and values for the
  class's variables.
- **Locked variables:** values a cluster can't change, enforced by a webhook.
- **Expiry:** a cron schedule. Each cluster expires at the schedule's next occurrence after it's
  created, and hyve-controller deletes it then.
- **Labels** on every cluster made from it.
- **A Fleet group:** hyve keeps a ClusterGroup, `template-<name>`, of every cluster made from
  it, so a [Deployment](/docs/concepts/deployments) aimed at the template reaches each one,
  including those made later.

The ClusterClass still describes how the cluster is built. The template describes which
clusters of that class people get. What goes on them is Deployments, which live beside the
template rather than in it.

## An example

```yaml
apiVersion: hyve.io/v1alpha1
kind: ClusterTemplate
metadata:
  name: civo-small
  namespace: capi-clusters          # the template namespace, beside its ClusterClass
spec:
  description: Civo K3s, one small node, gone by 8 pm
  clusterClassRef:
    name: civo                      # namespace defaults to the template's
  kubernetesVersion: v1.35.0        # default: the class's hyve.io/default-version
  variables:                        # defaults for the ClusterClass's variables
    region: NYC1
    nodeSize: g4s.kube.small
    nodeCount: 1
    credentialsSecret: civo-credentials
  lockedVariables: [region, credentialsSecret]
  schedule: CRON_TZ=America/Chicago 0 20 * * *
  labels:
    team: platform                  # on every Cluster; Fleet sees it through CAAPF
```

```bash
# what goes on its clusters: a Deployment aimed at it
hyve deploy create podinfo --helm podinfo --repo https://stefanprodan.github.io/podinfo \
    --version 6.7.1 -N podinfo --to template/civo-small
```

## Fields

| Field | What it does |
|---|---|
| `clusterClassRef.name`, `.namespace` | The ClusterClass to build from. Required. The namespace defaults to the template's own. |
| `kubernetesVersion` | The version clusters get unless they give one. Without it, the ClusterClass's `hyve.io/default-version` annotation is used. |
| `controlPlane.replicas` | Control-plane replicas for a machine-based control plane (kubeadm). Default 1. Ignored for a managed control plane (GKE, EKS, AKS), which has none. |
| `workers.type` | `machineDeployment` or `machinePool`. Default: whichever the ClusterClass defines. |
| `workers.class` | The worker class. Default: the ClusterClass's first of that type. |
| `workers.count` | Worker replicas. Default 1. |
| `variables` | Defaults for the ClusterClass's variables. A cluster may set others, and may override these unless they're locked. A variable set to `null` has no default here, so the class's own applies. |
| `lockedVariables` | Variables clusters can't change. Each must be listed in `variables`, with the value clusters keep. `kubernetesVersion` in this list locks the version to the template's `kubernetesVersion`. |
| `schedule` | A standard 5-field cron expression, in UTC unless prefixed with `CRON_TZ=<zone>`. |
| `labels` | Extra labels on every Cluster made from the template. |
| `resources` | Deprecated. hyve-controller turns each entry into a [Deployment](/docs/concepts/deployments#migrating-from-template-resources) aimed at the template and empties the list. Use Deployments instead. |
| `adopt.idVariable`, `adopt.variables`, `adopt.unset` | Lets `hyve cluster adopt` take over an existing cluster through the provider: the variable that takes its ID, values used in place of `variables` on adopted clusters, and variables left unset there, so the cluster keeps its own. Adopted clusters take no `schedule`. See [Bringing in existing clusters](/docs/guides/existing-clusters). |
| `description` | Shown by `hyve template list` and the UI. |

## How a cluster is made from a template

A cluster is made from a template by creating a CAPI `Cluster` labelled
`hyve.io/template: <name>` (and `hyve.io/template-namespace` when the template is in another
namespace). hyve-controller's mutating webhook fills it in when it's created, whoever creates
it: `hyve cluster create`, `kubectl apply`, a GitOps tool or the UI. So there is one path, and
the template's rules apply to all of them.

When it fills in a Cluster, the webhook:

- sets the class (`spec.topology.classRef`), with its namespace when it's another;
- sets the version, control-plane replicas and workers when the Cluster doesn't give them;
- sets each variable the Cluster doesn't set from the template's `variables`;
- adds the ClusterClass's `hyve.io/cluster-labels`, the template's `labels`, the template
  labels, `hyve.io/environment` and `hyve.io/cluster`, and `app.kubernetes.io/managed-by: hyve`;
- sets the default cluster network (`10.244.0.0/16` for pods, `10.128.0.0/12` for services)
  when the Cluster has none;
- sets `hyve.io/expires-at` from the schedule, unless the Cluster already has one.

What the Cluster already sets is kept, with two exceptions. It can't name a different class
from the template's. And it can't set a locked variable to a different value. A second,
validating webhook refuses that on every later update too, so the UI and `kubectl edit` can't
get around a lock. A cluster made before a lock was added keeps its value; only changing it is
refused.

`hyve template render` runs the same fill on your machine, with no cluster:

```bash
hyve template render -f template.yaml -f clusterclass.yaml --name demo -e dev --set nodeCount=2
```

Without the ClusterClass among the files, the class's defaults (version, workers) can't be
filled in.

## The ClusterClass's annotations

Two annotations on a ClusterClass are read by hyve:

| Annotation | What it does |
|---|---|
| `hyve.io/default-version` | The Kubernetes version used when neither the cluster nor the template gives one. |
| `hyve.io/cluster-labels` | `k=v,k2=v2`: labels every Cluster of the class gets, for example the label a CNI `ClusterResourceSet` selects. |

## Getting a ClusterClass

Installing a provider installs its CRDs and controller, not a ClusterClass. As with
clusterctl, a provider publishes its ClusterClasses beside its components manifest, as
`clusterclass-NAME.yaml`. `--clusterclass` installs one with the provider, in the template
namespace:

```bash
hyve provider add civo --clusterclass civo \
    --fetch-url https://github.com/cbridges1/cluster-api-provider-civo/releases/v0.2.0/infrastructure-components.yaml
```

In the UI, **Add provider** has a ClusterClasses field that does the same. Running it again
with a newer release updates the class.

A class of your own, or a provider's you've changed, goes in like a template:
`hyve template apply -f clusterclass.yaml` (or **Apply YAML** on the Templates page) takes a
ClusterClass and the provider templates it refers to (`CivoClusterTemplate`,
`KubeadmControlPlaneTemplate` and so on).

## Where templates live

A template lives in the same namespace as its ClusterClass: a **template namespace**,
`capi-clusters` by default. Clusters live in [environments](/docs/concepts/environments), other
namespaces, and use the class from the template namespace (`spec.topology.classRef.namespace`).

That's the layout CAAPF, Cluster API's Fleet add-on provider, is built for. Deployments aimed at
a template live in the template namespace and target its group, `template-<name>`. CAAPF copies
each CAPI Cluster's labels onto its Fleet Cluster and maps the cluster's namespace into the
class's namespace with a `BundleNamespaceMapping`, so those Deployments reach clusters in every
environment. hyve keeps the template's group in the template namespace and in every environment,
since Fleet looks groups up in each cluster's own namespace (see
[Groups](/docs/concepts/deployments#groups)).

<Aside>
Whoever can write the template namespace can deliver to every cluster built from its classes.
That's the point of a template, so give write access there only to platform admins.
Environment members can read it, which is enough to pick a template.
</Aside>

You can have more than one template namespace. `--template-namespace` picks one per command,
and `hyve env use NAME --template-namespace NS` saves one for the current server.

## Commands

```bash
hyve template create capd-small --class capd --workers 1 --schedule "0 20 * * *"
hyve template create gke-small --from-clusterclass gke --set project=my-proj --lock project
hyve template apply -f template.yaml          # anything more: write the YAML
hyve template list
hyve template show civo-small                  # the Deployments that reach it, and its clusters
hyve template delete civo-small
```

`--from-clusterclass` copies every variable the ClusterClass declares, with its default (or
`null`), as a starting point to edit. `--dry-run` prints the template instead of creating it.

Deleting a template deletes its group, so Deployments aimed at it no longer reach its clusters,
and Fleet removes what they deployed there. The Deployments themselves stay, as do the clusters,
with their variables.
