A hyve cluster is a plain Cluster API `Cluster` (`cluster.x-k8s.io/v1beta2`) in an
[environment](/docs/concepts/environments) namespace. hyve has no cluster object of its own.
Cluster API and its providers build the cluster; hyve fills it in from its template, keeps the
template's locks, gives it an expiry, delivers its resources through Fleet, and lets people
reach it through the host.

## Made from a template

A Cluster labelled `hyve.io/template` is filled in from that [template](/docs/concepts/templates)
by hyve-controller's webhook when it's created. All of these make the same cluster:

```bash
hyve cluster create demo --template civo-small -e dev
```

```yaml
# kubectl apply -f, a GitOps repo, or the UI
apiVersion: cluster.x-k8s.io/v1beta2
kind: Cluster
metadata:
  name: demo
  namespace: dev
  labels:
    hyve.io/template: civo-small
    hyve.io/template-namespace: capi-clusters   # when the template is in another namespace
spec:
  topology:
    variables:
      - name: nodeCount
        value: 2
```

The webhook adds the class, version, workers, the template's variables and labels, and the
expiry, and refuses the Cluster if it changes a locked variable. `hyve cluster create --dry-run`
prints the filled-in Cluster instead of creating it.

You can also make a cluster straight from a ClusterClass, with no template:

```bash
hyve cluster create demo --class capd --class-namespace capi-clusters
```

Then nothing is locked, nothing expires unless you say so, and no template resources are
delivered.

## Clusters hyve didn't create

A cluster made some other way can be brought in. `hyve cluster import` attaches any cluster you
have a kubeconfig for, without hyve managing its lifecycle. `hyve cluster adopt` has a provider
that supports it take over an existing cluster by ID. See
[Bringing in existing clusters](/docs/guides/existing-clusters).

`hyve cluster create` waits until the cluster is active and registered with Fleet (`--no-wait`
returns once the object exists; `--timeout` defaults to 30 minutes). `--set` sets ClusterClass
variables: a value is parsed as JSON when it's valid JSON (numbers, lists, objects) and used as
a string otherwise.

## Expiry

A cluster's expiry is its `hyve.io/expires-at` annotation: an RFC 3339 time, or `never`.
hyve-controller deletes the cluster when that time passes.

| Where it comes from | |
|---|---|
| The template's `schedule` | Set when the cluster is created: the schedule's next occurrence. |
| `hyve cluster create --ttl 4h` | That long after creation, replacing the template's schedule. |
| `hyve cluster create --no-expiry` | `never`, whatever the template says. |
| `hyve cluster expire NAME --in 8h`, `--at TIME`, `--never` | Changes it later. |

<Aside>
Expiry needs hyve-controller running at the time. In [local mode](/docs/running/local-mode), a
laptop that's off past a cluster's expiry deletes the cluster when it next starts.
</Aside>

## Who owns it

The webhook records who created a cluster in its `hyve.io/creator` annotation, from the API
server's view of the request, not the client's. hyve-controller then gives that user an
`owner` [ClusterAccess](/docs/concepts/access) on the cluster. That's how an environment member,
who can create clusters but not delete arbitrary ones, can delete their own.

## Changing a cluster

| Command | What it changes |
|---|---|
| `hyve cluster scale NAME --workers N` / `--control-plane N` | Worker or control-plane replicas. |
| `hyve cluster upgrade NAME --version v1.35.2` | `spec.topology.version`. Cluster API rolls the control plane, then the workers, one machine at a time. It refuses skipping a minor version or going back, and the class's providers must support the version. A template that locks `kubernetesVersion` keeps its clusters at its own. |
| `hyve cluster expire NAME ...` | Its expiry (above). |
| `hyve cluster resource add/remove CLUSTER ...` | Its extras: resources for this cluster only (see [Resources](/docs/concepts/resources)). |

Any other change is an edit to the `Cluster` object, as with any Cluster API cluster. Locked
variables stay locked.

## Seeing it

```bash
hyve cluster list                 # in the current environment; -A for every environment
hyve cluster show demo            # spec, Fleet state, resources and conditions
hyve cluster resource list demo   # its template's resources and its extras
hyve resource status demo         # what's on it, why, and its state
```

## Reaching it

The host proxies each cluster at `<url>/k8s/clusters/<environment>.<name>`, as you, with your
own permissions:

```bash
hyve cluster auth demo                   # adds it to ~/.kube/config and switches kubectl to it
hyve cluster kubeconfig demo > demo.yaml # or print it
```

Neither kubeconfig holds a secret: its credential is `hyve token`, your current session. The
cluster's admin credentials are never handed out. See [kubectl access](/docs/guides/kubectl-access)
and [Delivery](/docs/concepts/delivery) for how the host reaches the cluster.

## Deleting it

```bash
hyve cluster delete demo
```

This deletes the `Cluster`. Its extras (`ClusterResource`s) go with it, and Cluster API deletes
the infrastructure. An imported cluster is detached instead and keeps running; an adopted one is
kept when its provider's deletion policy says so. By default the command waits until the cluster is gone (up to 15 minutes;
`--wait=false` doesn't wait).
