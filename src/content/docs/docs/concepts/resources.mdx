What hyve puts on a cluster is its **template's resources** plus that cluster's own
**extras**. hyve has no resource format of its own. Each resource embeds one of Fleet's specs,
without targets:

| Key | Fleet kind | For |
|---|---|---|
| `helmOp` | `HelmOp` | A Helm chart from a repository or an `oci://` URL. |
| `bundle` | `Bundle` | Manifests given inline. |
| `gitRepo` | `GitRepo` | Manifests, charts or Kustomize from a git repository. |
| `ref` | (the shared Resource's) | A shared `Resource` defined once, used by name. |

hyve-controller turns each one into a Fleet object aimed at the right clusters, and Fleet does
the rest: per-cluster values like `${ .ClusterName }`, rollout, status and drift.

## Three places a resource can be

**On a template**, for every cluster made from it: an entry in the ClusterTemplate's
`resources`.

```yaml
# in a ClusterTemplate's spec
resources:
  - name: podinfo
    namespace: podinfo                 # on the cluster, unless the Fleet spec sets one
    helmOp:
      helm:
        repo: https://stefanprodan.github.io/podinfo
        chart: podinfo
        version: 6.7.1
        values:
          ui:
            message: ${ .ClusterName }
```

**Shared**, defined once and referred to by name: a `Resource` in the template namespace. It has
no targets of its own; it's delivered only where a template or extra refers to it.

```yaml
apiVersion: hyve.io/v1alpha1
kind: Resource
metadata:
  name: external-dns
  namespace: capi-clusters
spec:
  namespace: external-dns
  secrets: [cloudflare-dns]            # copied to each cluster it's delivered to
  helmOp:
    helm:
      repo: https://kubernetes-sigs.github.io/external-dns/
      chart: external-dns
      version: 1.19.0
      values:
        provider: {name: cloudflare}
```

```yaml
# a template entry using it
resources:
  - name: external-dns
    ref: external-dns
    values:                            # merged over the shared Resource's Helm values
      domainFilters: [example.com]
```

**On one cluster**, as an extra: a `ClusterResource` in the cluster's environment, with
`clusterName`. It doesn't change the cluster's template.

```yaml
apiVersion: hyve.io/v1alpha1
kind: ClusterResource
metadata:
  name: demo-monitoring
  namespace: dev
spec:
  clusterName: demo
  namespace: monitoring
  gitRepo:
    repo: https://github.com/example/monitoring.git
    branch: main
    paths: [prod]
```

## Fields every resource has

| Field | |
|---|---|
| `name` | The entry's name in a template; a `Resource`'s or `ClusterResource`'s is its `metadata.name`. A DNS label of at most 40 characters. It's also the Helm release name unless the HelmOp sets `releaseName`. |
| `namespace` | The namespace on the cluster for its objects, unless the Fleet spec sets `defaultNamespace` (or a GitRepo's `targetNamespace`). |
| `secrets` | Secrets in the owner's namespace that Fleet copies to each cluster (`downstreamResources`). See [Secrets](/docs/concepts/secrets). A `gitRepo` can't list them; put them in its `fleet.yaml` instead. |
| `ref`, `refNamespace` | A shared Resource to use. A shared Resource can't itself be a `ref`. |
| `values` | With `ref` only: merged over the shared Resource's Helm values (a HelmOp's). Otherwise put Helm values in `helmOp.helm.values`. |

Exactly one of `helmOp`, `bundle`, `gitRepo` or `ref` is set. Leave out `targets`: hyve sets
them.

A `ref` without `refNamespace` is looked up in the template's namespace. For a
`ClusterResource`, it's looked up beside the cluster's template first, then in the
`ClusterResource`'s own namespace.

## What hyve-controller creates

One Fleet object per resource, owned by what it came from:

| From | Fleet object | Where | Aimed at |
|---|---|---|---|
| A template's entry | `tpl-<template>-<name>` | The template namespace | Clusters labelled `hyve.io/template` and `hyve.io/template-namespace` with that template |
| A `ClusterResource` | Its own name | The cluster's environment | That one cluster, by name |

CAAPF names each Fleet Cluster after its CAPI Cluster and copies its labels, so these targets
work, and its `BundleNamespaceMapping` carries the template's objects to clusters in other
namespaces.

Because each Fleet object is owned by its template or `ClusterResource`, removing the resource,
deleting the template or deleting the cluster deletes the Fleet object, and Fleet removes what
it deployed. Deleting a shared `Resource` doesn't remove anything: the templates and extras
that refer to it report it missing.

Each owner's status lists its Fleet objects with Fleet's state, the Secrets that are missing,
and a `Ready` condition (`SecretsMissing` while any are).

## Commands

```bash
# every cluster made from a template
hyve template resource add civo-small --helm traefik --repo https://traefik.github.io/charts \
    --version 37.1.0 -N traefik --set service.type=LoadBalancer
hyve template resource add civo-small --ref external-dns --secret cloudflare-dns
hyve template resource remove civo-small traefik

# one cluster
hyve cluster resource add demo --path ./manifests --name base
hyve cluster resource remove demo base

# shared definitions
hyve resource create --name external-dns --helm external-dns \
    --repo https://kubernetes-sigs.github.io/external-dns/ --version 1.19.0 \
    -N external-dns -f external-dns-values.yaml --secret cloudflare-dns
hyve resource list
hyve resource show external-dns
hyve resource delete external-dns

# YAML
hyve resource apply -f resources.yaml
```

`--path` sends local manifests (a file, or a directory of `.yaml`, `.yml` and `.json`) inline as
a Bundle. In YAML given to `apply`, a `bundle` entry may give `path: DIR` instead of
`resources`, relative to the file. `--correct-drift` has Fleet undo changes made to its objects
on the cluster.

## Why something is on a cluster

```bash
hyve resource status demo
```

```
NAME              WHY                       KIND      SOURCE                                                STATE
podinfo           template civo-small       HelmOp    https://stefanprodan.github.io/podinfo podinfo@6.7.1  Ready
demo-monitoring   extra (demo-monitoring)   GitRepo   https://github.com/example/monitoring.git@main prod   Ready
```

`hyve resource status --template civo-small` shows a matrix instead: each of the template's
resources on each of its clusters.

<Aside>
The state is Fleet's, rolled up from each cluster's BundleDeployment. It's the same whether the
cluster's agent delivers it or hyve pushes it (see [Delivery](/docs/concepts/delivery)).
</Aside>
