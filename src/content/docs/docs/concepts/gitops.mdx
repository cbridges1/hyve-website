Hyve's core model is: a cluster is one YAML file in a local directory, and `hyve reconcile` makes reality match whatever that file says — created, updated, or deleted. That directory doesn't need to be anything more than a folder on disk (see [Environments](/docs/concepts/repositories)). Putting it under git is entirely your own choice, not a requirement — but it's a natural fit, applying the same version control, review, and continuous-reconciliation discipline to infrastructure that's already applied to application code (the pattern commonly called "GitOps"). This page covers that optional layer.

## The core loop

```yaml
# clusters/production.yaml
apiVersion: hyve.io/v1alpha1
kind: ClusterDefinition
metadata:
  name: production
spec:
  region: PHX1
  driver:
    source: github.com/hyve-modules/civo
    version: v1.0.0
  params:
    node_size: g4s.kube.large
    node_count: "3"
```

```bash
hyve reconcile
```

Commit that file and reconcile creates the cluster. Edit `node_count` and reconcile scales it. Delete the file and reconcile tears it down. One command, three outcomes, depending purely on what's in the directory `hyve env` currently points at — see [Environments](/docs/concepts/repositories).

## Hyve does not sync git for you

<Warning>
  This is deliberate, not a missing feature: hyve reads and writes plain files in whatever local directory is active. It never pulls before running, and never commits or pushes what it writes back (`driverOutputs`, applied-resource tracking) afterward. Syncing with a remote — if you're using one at all — is entirely your own `git` CLI, run by hand or from CI.
</Warning>

```bash
# Before reconciling, get the latest state yourself
git pull

hyve reconcile

# After reconciling, hyve may have written state back to
# cluster-state/*.state.yaml — commit and push that yourself too
git add -A && git commit -m "hyve: reconcile" && git push
```

<Tip>
  In CI/CD, this is exactly the pattern: `git pull && hyve reconcile && git commit -am "..." && git push` as pipeline steps — no separate "sync" feature to configure. Don't want a git remote at all? [Environments](/docs/concepts/repositories) work against any plain local directory, tracked or not.
</Tip>

## A real change, end to end

<Steps>
  <Step title="Branch">
    ```bash
    git checkout -b scale-production
    ```
  </Step>

  <Step title="Edit the cluster definition">
    Change `node_count` in `clusters/production.yaml` — no CLI command needed, it's just a file.
  </Step>

  <Step title="Preview, then commit">
    ```bash
    hyve reconcile --dry-run
    git commit -am "Scale production to 5 nodes for holiday traffic"
    git push origin scale-production
    ```
  </Step>

  <Step title="Review">
    Open a pull request — the diff *is* the change, reviewable like any code change.
  </Step>

  <Step title="Merge and reconcile">
    ```bash
    git checkout main && git pull
    hyve reconcile
    ```
  </Step>
</Steps>

## Disaster recovery

<Steps>
  <Step title="Clone your state repository">
    ```bash
    git clone https://github.com/your-org/your-hyve-config.git
    cd your-hyve-config
    ```
  </Step>

  <Step title="Point hyve at it">
    ```bash
    hyve env create prod --path .
    hyve env use prod
    ```
  </Step>

  <Step title="Reconcile">
    ```bash
    hyve reconcile
    # Recreates every cluster defined in the directory
    ```
  </Step>
</Steps>

<Note>
  This works the same whether or not the directory is git-backed — reconcile only cares about the files that are there.
</Note>

## Best practices

<AccordionGroup>
  <Accordion title="Descriptive commit messages">
    `git commit -m "Scale production for holiday traffic"`, not `git commit -m "update"` — this is your audit trail, since hyve keeps none of its own.
  </Accordion>

  <Accordion title="Review production changes via pull request">
    A cluster YAML diff is a normal code diff — branch, push, open a PR, merge, then reconcile.
  </Accordion>

  <Accordion title="Separate environments, separate directories">
    One `hyve env` per environment (`hyve env create prod --path ...`, `hyve env create staging --path ...`) keeps production and staging changes from ever touching the same reconcile run — see [Environments](/docs/concepts/repositories).
  </Accordion>

  <Accordion title="Automate reconciliation in CI">
    `git pull && hyve reconcile --dry-run` on every PR, `git pull && hyve reconcile` on merge to main — no extra orchestration needed.
  </Accordion>
</AccordionGroup>
