A single [cluster-mode](/docs/concepts/cluster-mode) install can serve many tenants at once. Each tenant is an **Organization** — a real row in hyve-api's own datastore (Postgres or SQLite, see `internal/orgdb`), not a Kubernetes object — paired with its own Kubernetes namespace and RBAC scaffolding. No separate Helm release per tenant, no separate controller+API pod pair to operate and upgrade for each one.

<Note>
  This is additive, not a replacement. Running one install per tenant namespace still works, and is the better choice when you want the strongest possible blast-radius isolation (a bug in one tenant's controller process can't touch another tenant's namespace at all, since it's a wholly separate process). Multi-tenancy is for the operational-scale case — many small tenants, most idle most of the time, where N Helm releases is a real, permanent cost.
</Note>

## Creating, renaming, and deleting organizations

```bash
hyve organization create acme
```

Superadmin-only, and deliberately narrow: it turns a name into a real tenant — its own namespace, its own `hyve-access-admin`/`hyve-access-readonly` `ServiceAccount`+`RoleBinding` scaffolding (the same RBAC a one-install-per-tenant deployment gets from the Helm chart at install time, created programmatically here instead), and its own datastore record — and nothing more. Every organization also gets one default **environment** automatically (a named sub-scope within it — `staging`, `production`, ... — see `hyve organization create-environment`).

Creating the tenant's first user is a separate, already-existing call:

```bash
hyve cluster-config api create-user alice --role admin --namespace acme
```

<Info>
  Each provisioning step checks "does this already exist" before acting — safe to re-run `hyve organization create` after a partial failure, no rollback needed.
</Info>

An organization's **name** can be changed later — its Kubernetes namespace, the thing every binding/RBAC/reconciling-cluster lookup actually keys on, never can, so this is purely a relabel:

```bash
hyve organization migrate --help   # renaming happens via the same PATCH /organizations/{name} as migration — see below
```

Names must stay unique, and the same two names creation reserves stay reserved for renaming too: `hyve-system` (the control plane's own namespace) and any casing/spacing of `control plane`.

Deleting one is equally direct:

```bash
hyve organization delete acme
```

This marks the row for deletion and issues a standard Kubernetes namespace delete — Kubernetes' own native cascade tears down everything inside it and then the namespace itself, no hyve-specific finalizer or out-of-band controller confirmation gates that removal. Deletion behaves the same way here as everywhere else in the application.

<Warning>
  The control plane's own organization (`hyve-system`) can never be deleted through this path, superadmin or not — it's the namespace `hyve-controller`/`hyve-api` themselves actually run in.
</Warning>

## Reconciling clusters: where a tenant's resources actually live

By default, an organization's `ClusterDefinition`/`Template`/`Workflow`/`Resource` objects (and its own `HyveConfig`) live in its namespace on the control plane's own home cluster, right alongside every other tenant's. A **reconciling cluster** lets one organization's resources live on a different, dedicated physical Kubernetes cluster instead — useful for isolating a noisy or sensitive tenant, or for a hosted offering that never wants tenant workloads anywhere near its own control-plane infrastructure.

This is entirely self-service — reachable by that organization's own `admin`, not just a superadmin — by registering a kubeconfig directly:

```bash
hyve reconciling-cluster create <name> --kubeconfig-file ./cell-a.yaml   # shared registry, superadmin-only
hyve organization migrate acme --reconciling-cluster <name>              # attach an already-registered one, superadmin-only
```

or, self-service, from the web console's own **Reconciling cluster** page (or the equivalent `PUT /organizations/{name}/reconciling-cluster` call) — paste a kubeconfig directly and it's registered as that organization's own dedicated cluster, migrating everything onto it in the same step. The console shows the cluster's server endpoint, its own reported Kubernetes version, and live reachability, and lets you edit (rotate) the stored kubeconfig or remove it entirely (migrating back to the home cluster first) at any time.

<Info>
  A dedicated reconciling cluster registered this way is named identically to the organization's own namespace — a deliberate 1:1 mapping that keeps it out of the shared superadmin-managed registry an ordinary admin has no visibility into.
</Info>

<Note>
  **The control plane is just another organization for this purpose.** `hyve-system` has a real Organization row of its own, and can be migrated onto its own reconciling cluster (or back to its literal home cluster) the exact same way — "Viewing: Control plane" in the web console resolves to `hyve-system`'s own namespace and renders the identical self-service Reconciling cluster page, just never showing any other organization's placement.
</Note>

### `--require-reconciling-cluster`

A hosted/managed install can refuse to let any organization other than the control plane's own ever land on (or migrate back to) the shared home cluster at all:

```bash
hyve cluster-config api run --require-reconciling-cluster ...
```

Every organization must then be given an explicit reconciling cluster at creation, and can never migrate back to `""` (home) later — a hard operator guarantee that tenant workloads never touch the infrastructure the control plane itself runs on.

## Namespace is chosen at login, not fixed at install time

Every access binding is scoped to a namespace (see [Access Control](/docs/concepts/access-control)), and which namespace a session resolves against is decided by the login request itself:

```bash
hyve env login --api-url https://hyve-api.example.com --org acme
```

`--org` is resolved **server-side**: it first looks for an organization currently named `acme` and, if found, logs into that organization's own (real, immutable) namespace — which may differ from `acme` if it's since been renamed. If no organization is registered under that exact name, the value is treated as a literal Kubernetes namespace directly, which is exactly how every organization that's never been renamed already behaves (name and namespace start out identical at creation). Either way, a login always resolves to the organization's real namespace, never a stale or renamed label.

Omit `--org` entirely to log in at the control-plane tier instead — see `superadmin` below.

## The `superadmin` role

Above the namespace-scoped `admin`/`read-only` roles sits one intentionally cluster-scoped tier: `superadmin`. It exists for a small, fixed set of things:

- Create, rename, or delete a tenant organization.
- Assign an organization to a cluster from the shared reconciling-cluster registry (self-service reconciling-cluster management, above, needs no `superadmin` at all).
- Access the [host cluster](#host-cluster-access) hyve's own controller/API run on.

It's never the default role, and no tenant `admin` can grant it to themselves — see [Access Control](/docs/concepts/access-control) for the full role model.

## Host cluster access

`hyve-controller`/`hyve-api` run *on* some cluster — the "host." Getting a kubeconfig for that cluster (not a cluster hyve *manages*, but the one running hyve *itself*) is its own path, gated to `superadmin` only:

```bash
hyve cluster auth <host-cluster-name>
```

The host cluster is a real `ClusterDefinition` like any other, with `spec.access.method: primary` — no `driver`, and `create`/`delete` refused outright (it already exists by definition; hyve can't provision or delete the cluster it's running on). The minted token is deliberately **full `cluster-admin`**, against a dedicated `hyve-host-admin` `ServiceAccount` — not a scoped-down role. The host cluster *is* the entire control plane (every tenant namespace, every controller/API pod, every Secret), so the safety here comes entirely from gating *who* can request the token, not from narrowing what it can do once granted. The token itself is short-lived (an hour by default, shorter than an ordinary login session) — re-run the command to refresh it.

<Warning>
  A tenant `admin` can never reach this, no matter how the request is scoped — it's a separate, superadmin-only authorization check on top of (not instead of) the namespace isolation everything else relies on.
</Warning>

## Moving tenants and hosts: `hyve migrate`

[`hyve migrate cluster`](/docs/cli/migrate#hyve-migrate-cluster) understands this model directly via `--namespace`, working alongside (not instead of) `hyve organization migrate` above:

- A tenant namespace scopes the migration to *just that tenant* — split one tenant onto its own dedicated cluster while the source keeps running for everyone else.
- `hyve-system` (the default) migrates *everything* — every organization, plus the control plane's own objects.
